# Add Sign-In

To add authentication to an ARDOR admin against an IGNIS API, configure `DefaultAuthProvider` and `DefaultAuthService` in an application configuration class, declare the sign-in endpoint in `noAuthPaths`, and supply a login page using `useLogin` from `ra-core`.

The following complete configuration file wires the default authentication provider, authentication options, and local storage service into the container:

```ts
import {
  type BaseArdorApplication as TArdorApplication,
  configuration,
  CoreBindings,
  DefaultAuthProvider,
  DefaultAuthService,
  DefaultRestDataProvider,
  inject,
  type IAuthProviderOptions,
  type IRestDataProviderOptions,
  provide,
} from '@venizia/ardor';

@configuration()
export class AuthConfiguration {
  constructor(
    @inject({ key: CoreBindings.APPLICATION_INSTANCE })
    private readonly application: TArdorApplication,
  ) {}

  @provide({ key: CoreBindings.REST_DATA_PROVIDER_OPTIONS })
  restDataProviderOptions(): IRestDataProviderOptions {
    return {
      url: '/api',
      noAuthPaths: ['/auth/sign-in'],
    };
  }

  @provide({ key: CoreBindings.AUTH_PROVIDER_OPTIONS })
  authProviderOptions(): IAuthProviderOptions {
    return {
      paths: {
        afterLogin: '/dashboard',
      },
    };
  }

  @provide({ key: CoreBindings.DEFAULT_REST_DATA_PROVIDER })
  restDataProvider() {
    return this.application.instantiate(DefaultRestDataProvider).value(this.application);
  }

  @provide({ key: CoreBindings.DEFAULT_AUTH_SERVICE })
  authService() {
    return this.application.instantiate(DefaultAuthService);
  }

  @provide({ key: CoreBindings.DEFAULT_AUTH_PROVIDER })
  authProvider() {
    return this.application.instantiate(DefaultAuthProvider).value(this.application);
  }
}
```

## 1. What default sign-in expects from IGNIS

ARDOR provides `DefaultAuthProvider` in `packages/admin/src/providers/auth.ts`, designed to integrate directly with an IGNIS authentication controller. When a user submits credentials, `DefaultAuthProvider.login` sends an HTTP `POST` request to `paths.signIn` (defaulting to `/auth/sign-in`) using `restDataProvider.send`.

The request body generated by `buildSignInBody` formats username and password credentials to match the IGNIS authentication contract:

```json
{
  "identifier": { "scheme": "username", "value": "admin" },
  "credential": { "scheme": "basic", "value": "password" }
}
```

The response payload is read by `readSignInSession`. The recommended response format returned by an IGNIS service is an object containing `userId`, optional `roles`, and a `token` object:

```json
{
  "userId": 1,
  "roles": ["admin", "editor"],
  "token": {
    "value": "eyJhbGciOiJIUzI1NiIsIn...",
    "type": "Bearer"
  }
}
```

`readSignInSession` also accepts `{ token: "<jwt>" }` where `token` is a bare JWT string. In this case, `DefaultAuthProvider` decodes the token claims without verifying the signature and extracts `userId` from the `userId` claim or the `sub` claim, and `type` defaults to `Bearer`. If neither the response body nor the JWT claims contain a valid user identifier, or if the token is missing, `login` throws an error and nothing is saved.

When the sign-in response resolves, `DefaultAuthProvider.saveSession` delegates to `DefaultAuthService.saveAuth` in `packages/kernel/src/base/services/auth.ts`. `saveAuth` writes session information into `localStorage` using keys defined in `packages/kernel/src/common/keys.ts`:

- `LocalStorageKeys.KEY_AUTH_TOKEN` (`@app/auth/token`): stores `JSON.stringify({ value, type, provider })`.
- `LocalStorageKeys.KEY_AUTH_IDENTITY` (`@app/auth/identity`): stores `JSON.stringify({ userId, username, referenceId, provider })`.
- `LocalStorageKeys.KEY_AUTH_PERMISSION` (`@app/auth/permission`): stores `JSON.stringify(roles)`.

Role names are extracted by `readRoleNames`: a string entry is preserved as a role name, while an object entry is identified by its `identifier` property (matching the IGNIS role model) or its `name` property.

## 2. Binding authentication in the configuration

Configuration classes decorated with `@configuration()` configure container services. Each method decorated with `@provide({ key })` registers an instance or options object into the container as a lazy singleton.

Five container bindings establish the authentication pipeline:

- `CoreBindings.REST_DATA_PROVIDER_OPTIONS`: provides `IRestDataProviderOptions` (defined in `packages/kernel/src/common/types.ts`). You must list `/auth/sign-in` in `noAuthPaths`. If the path is omitted from `noAuthPaths`, `DefaultNetworkRequestService` throws a 401 error before sending the request because no token exists in storage yet.
- `CoreBindings.AUTH_PROVIDER_OPTIONS`: provides `IAuthProviderOptions`. The post-login redirect path is configured through `paths.afterLogin` (defaulting to `/`).
- `CoreBindings.DEFAULT_AUTH_SERVICE`: provides `DefaultAuthService`, which manages token storage and session identity in `localStorage`.
- `CoreBindings.DEFAULT_AUTH_PROVIDER`: provides `DefaultAuthProvider`, exposing methods consumed by react-admin.
- `CoreBindings.DEFAULT_REST_DATA_PROVIDER`: provides the data provider that executes network calls.

For complete details on application bootstrapping and configuration classes, see [Application](../core-concepts/application) and [Configuration](../core-concepts/configuration).

## 3. The login page

The login page renders the form where users enter their credentials and submits them using react-admin's `useLogin` hook from `ra-core`.

Create `src/pages/login.tsx`:

```tsx
import { useState, type FormEvent } from 'react';
import { useLogin, useNotify } from 'ra-core';

export const LoginPage = () => {
  const login = useLogin();
  const notify = useNotify();
  const [username, setUsername] = useState('');
  const [password, setPassword] = useState('');

  const submit = (event: FormEvent) => {
    event.preventDefault();
    login({ username, password }).catch(() => {
      notify('ra.auth.sign_in_error', { type: 'error' });
    });
  };

  return (
    <form onSubmit={submit}>
      <h1>Sign in</h1>
      <label>
        Username{' '}
        <input
          name="username"
          value={username}
          onChange={(event) => setUsername(event.target.value)}
        />
      </label>
      <label>
        Password{' '}
        <input
          name="password"
          type="password"
          value={password}
          onChange={(event) => setPassword(event.target.value)}
        />
      </label>
      <button type="submit">Sign in</button>
    </form>
  );
};
```

`LoginPage` goes to the `loginPage` prop of `ArdorApplication`, as in `src/main.tsx` of the [5-minute quickstart](../get-started/5-minute-quickstart).

When an unauthenticated user accesses a protected route, `DefaultAuthProvider.checkAuth()` verifies whether a token is present in storage via `authService.getAuth()`. If no valid token exists, `checkAuth` rejects with `{ redirectTo: '/login' }`, directing the user to the login form.

## 4. Protecting pages and components by role

`DefaultAuthProvider` offers several methods to inspect authentication state and permissions:

- `checkAuth`: resolves if a token exists in `localStorage`. If `paths.checkAuth` is configured in `IAuthProviderOptions`, it issues a `GET` request to validate the token against the backend.
- `getRoles`: reads what `login` saved in `localStorage` and resolves with a `Set<string>`. Roles come from the response `roles`, else from the token's `roles` claim (see `readSignInSession` in `packages/admin/src/providers/auth.ts`).
- `getIdentity`: reads `@app/auth/identity` through `authService.getUser()` and returns `{ userId, username, referenceId, provider }`.
- `getPermissions`: resolves with nothing in the default class (`Promise.resolve()`) and can be overridden if custom permission objects are required.

To authorize UI components and resources through react-admin's `canAccess` contract (used by `useCanAccess` and `<CanAccess>`), bind an implementation of `IPermissionProvider` under `CoreBindings.PERMISSION_PROVIDER`. When this binding is present, `DefaultAuthProvider.value()` attaches `canAccess` to the authentication provider. If `PERMISSION_PROVIDER` is not bound, `canAccess` remains undefined and react-admin permits access to all actions.

Create `src/configurations/permission.configuration.ts`:

```ts
import {
  configuration,
  CoreBindings,
  DefaultAuthService,
  inject,
  type IPermissionProvider,
  provide,
} from '@venizia/ardor';

@configuration()
export class PermissionConfiguration {
  constructor(
    @inject({ key: CoreBindings.DEFAULT_AUTH_SERVICE })
    private readonly authService: DefaultAuthService,
  ) {}

  @provide({ key: CoreBindings.PERMISSION_PROVIDER })
  permissionProvider(): IPermissionProvider {
    return {
      canAccess: async ({ resource, action }) => {
        const roles = this.authService.getRoles();
        if (roles.has('admin')) {
          return true;
        }
        if (roles.has('editor') && action !== 'delete') {
          return true;
        }
        return false;
      },
    };
  }
}
```

You can now protect specific buttons, views, or actions in your React components using `useCanAccess` from `ra-core`:

```tsx
import { useCanAccess } from 'ra-core';

export const DeleteButton = () => {
  const { canAccess, isPending } = useCanAccess({
    resource: 'configurations',
    action: 'delete',
  });

  if (isPending || !canAccess) {
    return null;
  }

  return <button type="button">Delete configuration</button>;
};
```

For more details on permission provider architecture, see [Permission provider](../../references/permission).

## 5. Token recovery and refresh

Authentication recovery ensures that an expired token does not interrupt user operations. When a request returns an HTTP 401 status code, `DefaultNetworkRequestService` evaluates `canRecover(paths)`:

1. The endpoint must not be a no-auth path (`isNoAuthPath`).
2. The endpoint must not match `authRecovery.refreshTokenPath`.

If both conditions pass, `DefaultNetworkRequestService.refresh()` executes. It batches concurrent failures during a 401 burst into a single in-flight promise. The service calls the protected hook `refreshToken()`. When `refreshToken()` resolves `true`, the failed request is retried once with the new authorization header. If `refreshToken()` throws, `onAuthFailure()` runs once, the refresh resolves `false`, and the original 401 error is raised.

To implement token refresh, subclass `DefaultNetworkRequestService` and `DefaultRestDataProvider` in `src/providers/app-rest-data.provider.ts`:

```ts
import {
  DefaultNetworkRequestService,
  DefaultRestDataProvider,
  LocalStorageKeys,
  RequestMethods,
  RequestTypes,
} from '@venizia/ardor';

export class AppNetworkService extends DefaultNetworkRequestService {
  protected override async refreshToken(): Promise<boolean> {
    const { data } = await this.doRequest<{ token: string }>({
      type: RequestTypes.SEND,
      method: RequestMethods.POST,
      paths: ['/auth/token/refresh'],
      headers: this.getRequestHeader({ resource: '/auth/token/refresh' }),
    });

    localStorage.setItem(
      LocalStorageKeys.KEY_AUTH_TOKEN,
      JSON.stringify({ value: data.token, type: 'Bearer' }),
    );
    return true;
  }
}

export class AppRestDataProvider extends DefaultRestDataProvider {
  protected override createNetworkService() {
    return new AppNetworkService({
      name: 'app-network-service',
      baseUrl: this.restDataProviderOptions.url,
      noAuthPaths: this.restDataProviderOptions.noAuthPaths,
      noAuthPathRegex: this.restDataProviderOptions.noAuthPathRegex,
      headers: this.restDataProviderOptions.headers,
      authRecovery: this.restDataProviderOptions.authRecovery,
    });
  }
}
```

Register `AppRestDataProvider` under `CoreBindings.DEFAULT_REST_DATA_PROVIDER`, configure `authRecovery: { refreshTokenPath: '/auth/token/refresh' }` in `REST_DATA_PROVIDER_OPTIONS`, and include `/auth/token/refresh` in `noAuthPaths`.

To trigger a token refresh manually from a component or background timer, use the `useRefreshToken` hook:

```tsx
import { useRefreshToken } from '@venizia/ardor';

export const RefreshButton = () => {
  const refreshToken = useRefreshToken();

  const handleRefresh = async () => {
    await refreshToken();
  };

  return (
    <button type="button" onClick={handleRefresh}>
      Refresh session
    </button>
  );
};
```

`useRefreshToken` calls `DefaultAuthProvider.refreshToken()`, which delegates to `restDataProvider.getNetworkService().refresh()`, and invalidates the query cache under `['auth', 'getPermissions']`. Because it uses the same network service method, manual refreshes and automatic 401 recoveries share the same coalesced promise.

For detailed guidelines on token recovery policies and error handling, see [No-auth paths and token recovery](../../best-practices/auth-recovery).

## 6. Sign out and error handling

To log a user out, call react-admin's `useLogout` hook:

```tsx
import { useLogout } from 'ra-core';

export const LogoutButton = () => {
  const logout = useLogout();

  return (
    <button type="button" onClick={() => logout()}>
      Sign out
    </button>
  );
};
```

Calling `logout()` invokes `DefaultAuthProvider.logout()`, which executes `DefaultAuthService.cleanUp()`. `cleanUp()` iterates through `localStorage` and deletes every key starting with `@app/auth/` or `@app/oauth2/`. Stored tokens, identities, and permissions are removed while unrelated application keys in `localStorage` are left intact.

`DefaultAuthProvider.checkError` evaluates HTTP errors raised by the data provider or react-admin:

- Status 401: calls `authService.cleanUp()` and rejects with `{ redirectTo: '/login' }`.
- Status 403: rejects with `{ redirectTo: '/unauthorized', logoutUser: false }`. The session is preserved and the user is redirected to the unauthorized error view without being logged out.

## 7. Your API signs in elsewhere

If your backend API exposes a non-standard sign-in route or expects a different request payload format, customize the route and payload mapping without replacing the entire authentication lifecycle.

Set `paths.signIn` in `IAuthProviderOptions` and add the matching path to `noAuthPaths` in `IRestDataProviderOptions`. To modify the request body format, subclass `DefaultAuthProvider` and override `buildSignInBody`:

```ts
import {
  type AnyType,
  type BaseArdorApplication as TArdorApplication,
  configuration,
  CoreBindings,
  DefaultAuthProvider,
  DefaultAuthService,
  DefaultRestDataProvider,
  inject,
  type IAuthProviderOptions,
  type IRestDataProviderOptions,
  provide,
} from '@venizia/ardor';

export class CustomAuthProvider extends DefaultAuthProvider {
  protected override buildSignInBody(opts: { params: AnyType }) {
    return {
      identifier: { scheme: 'email', value: opts.params?.email },
      credential: { scheme: 'basic', value: opts.params?.password },
    };
  }
}

@configuration()
export class CustomAuthConfiguration {
  constructor(
    @inject({ key: CoreBindings.APPLICATION_INSTANCE })
    private readonly application: TArdorApplication,
  ) {}

  @provide({ key: CoreBindings.REST_DATA_PROVIDER_OPTIONS })
  restDataProviderOptions(): IRestDataProviderOptions {
    return {
      url: '/api',
      noAuthPaths: ['/auth/login'],
    };
  }

  @provide({ key: CoreBindings.AUTH_PROVIDER_OPTIONS })
  authProviderOptions(): IAuthProviderOptions {
    return {
      paths: {
        signIn: '/auth/login',
        afterLogin: '/dashboard',
      },
    };
  }

  @provide({ key: CoreBindings.DEFAULT_REST_DATA_PROVIDER })
  restDataProvider() {
    return this.application.instantiate(DefaultRestDataProvider).value(this.application);
  }

  @provide({ key: CoreBindings.DEFAULT_AUTH_SERVICE })
  authService() {
    return this.application.instantiate(DefaultAuthService);
  }

  @provide({ key: CoreBindings.DEFAULT_AUTH_PROVIDER })
  authProvider() {
    return this.application.instantiate(CustomAuthProvider).value(this.application);
  }
}
```

If your API expects the plain login form object without schema wrapping, `buildSignInBody` can return `opts.params` directly:

```ts
import { type AnyType, DefaultAuthProvider } from '@venizia/ardor';

export class FormAuthProvider extends DefaultAuthProvider {
  protected override buildSignInBody(opts: { params: AnyType }) {
    return opts.params;
  }
}
```

> [!NOTE]
> If an application requires no authentication at all, leave `CoreBindings.DEFAULT_AUTH_PROVIDER` unbound, omit `loginPage` on `ArdorApplication`, and configure `noAuthPathRegex: /./` on `REST_DATA_PROVIDER_OPTIONS`. `ArdorApplication` then runs without an authentication provider and keeps all routes public.
