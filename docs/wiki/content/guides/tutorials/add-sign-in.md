# Add Sign-In

Turn sign-in on by binding the auth options `{ use: true, paths }` in an application configuration class, declare the sign-in endpoint in `noAuthPaths`, and supply a login page. `BaseArdorApplication` binds `DefaultAuthProvider` and `DefaultAuthService` itself, so you bind options only:

```ts
import {
  configuration,
  CoreBindings,
  type IRestDataProviderOptions,
  provideOption,
  type TAuthProviderOptions,
} from '@venizia/ardor';

@configuration()
export class AuthConfiguration {
  @provideOption({ key: CoreBindings.REST_DATA_PROVIDER_OPTIONS })
  restDataProviderOptions(): IRestDataProviderOptions {
    return { url: '/api', noAuthPaths: ['/auth/sign-in'] };
  }

  @provideOption({ key: CoreBindings.AUTH_PROVIDER_OPTIONS })
  authProviderOptions(): TAuthProviderOptions {
    return { use: true, paths: { afterLogin: '/dashboard' } };
  }
}
```

`@configuration()` registers the class, and the build finds it. `use: true` is what turns sign-in on: without it, or with `{ use: false }`, the app has no sign-in and every page is public.

## 1. What default sign-in expects from IGNIS

`DefaultAuthProvider.login` (`packages/admin/src/providers/auth.ts`) sends an HTTP `POST` request to `paths.signIn` (default `/auth/sign-in`) using `restDataProvider.send`.

Request body generated by `buildSignInBody`:

```json
{
  "identifier": { "scheme": "username", "value": "admin" },
  "credential": { "scheme": "basic", "value": "password" }
}
```

Response payload read by `readSignInSession`:

```json
{
  "userId": 1,
  "roles": ["admin", "editor"],
  "token": { "value": "eyJhbGciOiJIUzI1NiIsIn...", "type": "Bearer" }
}
```

`readSignInSession` also accepts `{ token: "<jwt>" }` (bare JWT string), decoding claims without signature verification to extract `userId` from `userId` or `sub`, defaulting `type` to `Bearer`. If no token or user identifier exists, `login` throws.

`DefaultAuthProvider.saveSession` delegates to `DefaultAuthService.saveAuth` (`packages/kernel/src/base/services/auth.ts`), writing to `localStorage`:

- `LocalStorageKeys.KEY_AUTH_TOKEN` (`@app/auth/token`): `JSON.stringify({ value, type, provider })`.
- `LocalStorageKeys.KEY_AUTH_IDENTITY` (`@app/auth/identity`): `JSON.stringify({ userId, username, referenceId, provider })`.
- `LocalStorageKeys.KEY_AUTH_PERMISSION` (`@app/auth/permission`): `JSON.stringify(roles)`.

`readRoleNames` preserves string entries as role names, and reads `identifier` or `name` on object entries.

## 2. Authentication container bindings

`AuthConfiguration` binds the options of the authentication pipeline; the base application binds what reads them:

- `CoreBindings.REST_DATA_PROVIDER_OPTIONS`: provides `IRestDataProviderOptions` (`packages/kernel/src/common/types.ts`). List `/auth/sign-in` in `noAuthPaths`; omitting it causes `DefaultNetworkRequestService` to throw 401 before sending because no token exists in storage.
- `CoreBindings.AUTH_PROVIDER_OPTIONS`: provides `TAuthProviderOptions`. `{ use: true }` turns sign-in on, and `paths.afterLogin` sets the post-login redirect (default `/`).
- `CoreBindings.DEFAULT_AUTH_SERVICE`: bound by the base application, `DefaultAuthService` manages tokens and identity in `localStorage`.
- `CoreBindings.DEFAULT_AUTH_PROVIDER`: bound by the base application, `DefaultAuthProvider` for react-admin. `ArdorApplication` resolves it only when `use` is `true`.
- `CoreBindings.DEFAULT_REST_DATA_PROVIDER`: bound by the base application, the data provider that executes network calls.

See [Configuration](../core-concepts/configuration).

## 3. The login page

The login page submits credentials using `useLogin` from `ra-core`:

```tsx
import { useState, type FormEvent } from 'react';
import { useLogin, useNotify } from 'ra-core';

export const LoginPage = () => {
  const login = useLogin();
  const notify = useNotify();
  const [username, setUsername] = useState('');
  const [password, setPassword] = useState('');

  const submit = (event: FormEvent) => {
    event.preventDefault();
    login({ username, password }).catch(() => {
      notify('ra.auth.sign_in_error', { type: 'error' });
    });
  };

  return (
    <form onSubmit={submit}>
      <h1>Sign in</h1>
      <label>
        Username <input value={username} onChange={(e) => setUsername(e.target.value)} />
      </label>
      <label>
        Password <input type="password" value={password} onChange={(e) => setPassword(e.target.value)} />
      </label>
      <button type="submit">Sign in</button>
    </form>
  );
};
```

Pass `LoginPage` to the `loginPage` prop of `ArdorApplication` ([Quickstart](../get-started/5-minute-quickstart)). When an unauthenticated user accesses a protected route, `DefaultAuthProvider.checkAuth()` checks storage via `authService.getAuth()`. If no valid token exists, `checkAuth` rejects with `{ redirectTo: '/login' }`.

## 4. Protecting pages and components by role

`DefaultAuthProvider` exposes inspection methods:

- `checkAuth`: resolves if a token exists in `localStorage`, or issues `GET` to `paths.checkAuth` if configured.
- `getRoles`: resolves with `Set<string>` of stored roles.
- `getIdentity`: reads `@app/auth/identity` through `authService.getUser()` (`{ userId, username, referenceId, provider }`; `{}` when nothing is stored) and resolves it with `id` set to `userId`. It rejects when there is no `userId`.
- `getPermissions`: resolves with nothing; the roles come from `getRoles`.

To authorize UI components and resources through react-admin's `canAccess` contract, bind a permission provider under `CoreBindings.PERMISSION_PROVIDER`. Unbound, `canAccess` remains undefined and react-admin permits access to all actions.

If you keep a table of roles and what each may do, ARDOR's `RolePermissionProvider` is that provider: write the table as options and bind the class. The roles are the role names `login` stored.

```ts
import { BindingScopes } from '@venizia/ignis-inversion';
import {
  BaseArdorApplication,
  configuration,
  CoreBindings,
  provideOption,
  RolePermissionProvider,
  type IApplicationInfo,
  type IRolePermissionProviderOptions,
} from '@venizia/ardor';

export class Roles {
  static readonly ADMIN = 'admin';
  static readonly EDITOR = 'editor';
}

@configuration()
export class PermissionConfiguration {
  @provideOption({ key: CoreBindings.PERMISSION_PROVIDER_OPTIONS })
  permissionOptions(): IRolePermissionProviderOptions {
    return {
      grants: {
        [Roles.ADMIN]: ['*'],
        [Roles.EDITOR]: ['orders.*', 'stocks.list', 'stocks.show'],
      },
    };
  }
}

export class ShopApplication extends BaseArdorApplication {
  getAppInfo(): IApplicationInfo {
    return { name: 'shop', version: '1.0.0', description: 'A shop back office' };
  }

  bindContext(): void {
    this.bind({ key: CoreBindings.PERMISSION_PROVIDER })
      .toClass(RolePermissionProvider)
      .setScope(BindingScopes.SINGLETON);
  }
}
```

Components check permissions with `useCanAccess` from `ra-core`, and read the roles with `Ardor.useRoles()`. For a source other than a role table, write your own `IPermissionProvider`. These checks decide what the interface shows: the backend must check every request. See [Permission provider](../../references/permission).

## 5. Token recovery and refresh

When a request returns HTTP 401, `DefaultNetworkRequestService` asks `AuthRecovery.canRecover({ paths })`: the endpoint must not be a no-auth path (`isNoAuthPath`) or match `authRecovery.refreshTokenPath`.

If both pass, `refresh()` batches concurrent 401 failures into a single in-flight promise and calls `refreshToken()`. Retried once if `refreshToken()` resolves `true`. If `refreshToken()` throws, `onAuthFailure()` runs once, the refresh resolves `false`, and the 401 error is raised.

Set `authRecovery: { refreshTokenPath: '/auth/token/refresh' }` in `REST_DATA_PROVIDER_OPTIONS`. The default `refreshToken()` POSTs to that path with no body, reads the new token from the answer and saves it through the auth service, so the session hooks run and the kept identity and roles stay. It needs no subclass. The expired token is attached to the refresh request, which is what an endpoint that reads the session from the token needs. Add the path to `noAuthPaths` only when the server identifies the session by other means, such as a cookie: that keeps the token off the request.

Write a `DefaultNetworkRequestService` subclass only for a refresh the default does not cover: a request body, another answer shape, or a token store that is not the auth service. See [The default refresh](../../best-practices/auth-recovery#the-default-refresh).

`Ardor.useRefreshToken()` calls `DefaultAuthProvider.refreshToken()`, which delegates to `refresh()` on the network service and shares the same coalesced promise. See [No-auth paths and token recovery](../../best-practices/auth-recovery).

## 6. Sign out and error handling

To log out, call `useLogout` from `ra-core`. `DefaultAuthProvider.logout()` invokes `DefaultAuthService.cleanUp()`, deleting the session keys under `keys.authPrefix` (`@app/auth/`, or `@app/auth/<id>/` for an application with an `id`) from `localStorage`, and `clearStoredData()` sweeps `@app/store/` in `localStorage` and `sessionStorage`.

`DefaultAuthProvider.checkError` evaluates HTTP errors raised by the data provider or react-admin:

- Status 401: calls `authService.cleanUp()` and rejects with `{ redirectTo: '/login' }`.
- Status 403: rejects with `{ redirectTo: '/access-denied', logoutUser: false }`. The user stays signed in and lands on the access-denied page `ArdorApplication` mounts: `AccessDeniedPage` (a title, a sentence and a link home), or the component you pass as `accessDenied`. react-admin sends a user whom `canAccess` denies a resource to the same page.

## 7. Custom sign-in route and body

Set `paths.signIn` in the auth options (`{ use: true, paths: { signIn } }`) and add the matching path to `noAuthPaths` in `IRestDataProviderOptions`. To modify the request body format, subclass `DefaultAuthProvider` and override `buildSignInBody`, then bind the subclass in place of the default in `bindContext()`:

```ts
import {
  BaseArdorApplication,
  CoreBindings,
  DefaultAuthProvider,
  type IApplicationInfo,
  type ILoginParams,
} from '@venizia/ardor';
import { BindingScopes } from '@venizia/ignis-inversion';

export class CustomAuthProvider extends DefaultAuthProvider {
  protected override buildSignInBody(opts: { params: ILoginParams }) {
    return {
      identifier: { scheme: 'email', value: opts.params.email },
      credential: { scheme: 'basic', value: opts.params.password },
    };
  }
}

export class ShopApplication extends BaseArdorApplication {
  getAppInfo(): IApplicationInfo {
    return { name: 'shop', version: '1.0.0', description: 'A shop back office' };
  }

  bindContext(): void {
    this.bind({ key: CoreBindings.DEFAULT_AUTH_PROVIDER })
      .toProvider(CustomAuthProvider)
      .setScope(BindingScopes.SINGLETON);
  }
}
```

The subclass keeps the constructor of `DefaultAuthProvider`, so the container supplies its dependencies, and `bindContext()` runs after the defaults, so this binding replaces the default.

To send the login form directly without schema wrapping, return `opts.params`.

> [!NOTE]
> If an application requires no authentication at all, bind `{ use: false }` for `CoreBindings.AUTH_PROVIDER_OPTIONS` (or bind nothing: unbound means the same), omit `loginPage` on `ArdorApplication`, and configure `noAuthPathRegex: /./` on `REST_DATA_PROVIDER_OPTIONS`.
