# Internationalization

`DefaultI18nProvider` creates the react-admin internationalization provider (`I18nProvider`) backed by `ra-i18n-polyglot`. It resolves message bundles and language options from the container, determines the startup locale from the browser, and merges feature-contributed translations with application overrides.

## What it does

`DefaultI18nProvider` reads `II18nProviderOptions` from the container to register available languages, load translated message bundles, and determine initial locale selection. Components retrieve localized strings through `useTranslate`, while complementary hooks synchronize the active locale with backend request headers, document titles, and root HTML attributes.

| Export | Kind | Meaning |
|---|---|---|
| `DefaultI18nProvider` | class | Provider that builds the react-admin `I18nProvider` from `II18nProviderOptions` |
| `II18nProviderOptions` | interface | Options defining `i18nSources` and `languages` |
| `englishMessages` | const | English translation bundle containing react-admin `ra.*` messages |
| `vietnameseMessages` | const | Vietnamese translation bundle containing react-admin `ra.*` messages |
| `useTranslate` | hook | Returns a typed `translate(key, options?)` function |
| `useRequestHeaderLocale` | hook | Synchronizes the active locale with REST data provider request headers |
| `useHtmlLang` | hook | Synchronizes document `<html lang>` with the active locale |
| `useDocumentTitle` | hook | Sets the document title and restores the previous title on unmount |
| `TUseTranslateFn` | type | Function signature returned by `useTranslate` |
| `TUseTranslateKeys` | type | Accepted keys: union of default keys and `IUseTranslateKeysOverrides` |
| `TUseTranslateKeysDefault` | type | `TFullPaths<typeof englishMessages>` |
| `IUseTranslateKeysOverrides` | interface | Overridable interface for augmenting application translation keys |
| `IUseRequestHeaderLocaleOptions` | interface | Options for `useRequestHeaderLocale` |
| `IUseDocumentTitleOptions` | interface | Options for `useDocumentTitle` |
| `CoreBindings.DEFAULT_I18N_PROVIDER` | const | Container binding key for the internationalization provider instance |
| `CoreBindings.I18N_PROVIDER_OPTIONS` | const | Container binding key for `II18nProviderOptions` |
| `HeaderConstants.X_LOCALE` | const | Default request header name (`'x-locale'`) used by `useRequestHeaderLocale` |

## How to provide it

The configuration class is the main way to configure ARDOR: a `@configuration()` class whose `@provide({ key })` methods return the options or the provider instances; `start()` binds each as a lazy SINGLETON. As described in [The bind order](../guides/core-concepts/configuration), the options and the provider on this page are bound by `@provide` methods of the application configuration class:

```ts
import {
  type BaseArdorApplication as TArdorApplication,
  configuration,
  CoreBindings,
  DefaultI18nProvider,
  englishMessages,
  type II18nProviderOptions,
  inject,
  provide,
  vietnameseMessages,
} from '@venizia/ardor';

@configuration()
export class I18nConfiguration {
  constructor(
    @inject({ key: CoreBindings.APPLICATION_INSTANCE })
    private readonly application: TArdorApplication,
  ) {}

  @provide({ key: CoreBindings.I18N_PROVIDER_OPTIONS })
  i18nProviderOptions(): II18nProviderOptions {
    return {
      i18nSources: {
        en: englishMessages,
        vi: vietnameseMessages,
      },
      languages: [
        { locale: 'en', name: 'English' },
        { locale: 'vi', name: 'Tiếng Việt' },
      ],
    };
  }

  @provide({ key: CoreBindings.DEFAULT_I18N_PROVIDER })
  i18nProvider() {
    return this.application.instantiate(DefaultI18nProvider).value(this.application);
  }
}
```

The configuration relies on the following default class and container keys:
- Default class: `DefaultI18nProvider` from `packages/admin/src/providers/i18n.ts`.
- Options key: `CoreBindings.I18N_PROVIDER_OPTIONS` (`@app/application/options/i18n`).
- Provider key: `CoreBindings.DEFAULT_I18N_PROVIDER` (`@app/application/i18n/default`).

Calling `this.application.instantiate(DefaultI18nProvider)` injects `I18N_PROVIDER_OPTIONS` and optional `FEATURES` from the container into the provider. Calling `.value(this.application)` extracts the react-admin `I18nProvider` passed to the application in [Application](./application).

## Options

`II18nProviderOptions` from `packages/admin/src/common/types.ts` defines the configuration options:

| Field | Type | Default | Meaning |
|---|---|---|---|
| `i18nSources` | `Record<string \| symbol, AnyType>` | `{ en: englishMessages }` | Dictionary mapping locale codes to translation message bundles. Merged with feature messages per locale. |
| `languages` | `Array<Locale>` | `[{ locale: 'en', name: 'English' }]` | Available locales with display names (`{ locale: string, name: string }`) passed to react-admin. |

Both options apply independently. If `languages` defines a locale code that is missing from `i18nSources`, selecting that locale resolves messages using `englishMessages`.

## Example

The following example configures English and Vietnamese messages for an administrative console. It extends `englishMessages` and `vietnameseMessages` with custom application keys under the `app` namespace:

```ts
import {
  type BaseArdorApplication as TArdorApplication,
  configuration,
  CoreBindings,
  DefaultI18nProvider,
  englishMessages,
  type II18nProviderOptions,
  inject,
  provide,
  vietnameseMessages,
} from '@venizia/ardor';

export const appEnglish = {
  ...englishMessages,
  app: {
    welcome: 'Welcome to the Dashboard',
    products: {
      title: 'Products',
      empty: 'No products found',
    },
  },
};

export const appVietnamese = {
  ...vietnameseMessages,
  app: {
    welcome: 'Chào mừng đến với Bảng điều khiển',
    products: {
      title: 'Sản phẩm',
      empty: 'Không tìm thấy sản phẩm nào',
    },
  },
};

@configuration()
export class StoreI18nConfiguration {
  constructor(
    @inject({ key: CoreBindings.APPLICATION_INSTANCE })
    private readonly application: TArdorApplication,
  ) {}

  @provide({ key: CoreBindings.I18N_PROVIDER_OPTIONS })
  i18nProviderOptions(): II18nProviderOptions {
    return {
      i18nSources: {
        en: appEnglish,
        vi: appVietnamese,
      },
      languages: [
        { locale: 'en', name: 'English' },
        { locale: 'vi', name: 'Tiếng Việt' },
      ],
    };
  }

  @provide({ key: CoreBindings.DEFAULT_I18N_PROVIDER })
  i18nProvider() {
    return this.application.instantiate(DefaultI18nProvider).value(this.application);
  }
}
```

## Locale resolution and fallback

In `packages/admin/src/providers/i18n.ts`, `DefaultI18nProvider.resolveInitialLocale` computes the startup locale when `value()` is called:

1. It reads `navigator.language` in browser environments (`typeof navigator !== 'undefined'`). If `navigator` is undefined or `navigator.language` is empty, it uses `'en-US'`.
2. It splits the language string on `-` and extracts the primary language subtag before the first hyphen (for example, `'en-US'` becomes `'en'`, and `'vi-VN'` becomes `'vi'`).
3. If the extracted language is present in the `languages` array, that language is selected.
4. Otherwise, it falls back to `'en'`.

| Browser language | Configured `languages` | Initial locale |
|---|---|---|
| `en-US` | `['en', 'vi']` | `en` |
| `vi-VN` | `['en', 'vi']` | `vi` |
| `fr-FR` | `['en', 'vi']` | `en` |
| `fr-FR` | `['vi']` | `en` |

> [!NOTE]
> The initial locale fallback is always `'en'`, even if `'en'` is not included in `languages`.

When rendering messages, `composeMessages` reads `i18nSources[locale]`. If that locale is not defined in `i18nSources`, it defaults to `englishMessages`. Missing translation keys do not throw: `polyglotI18nProvider` sets `allowMissing: true` and `onMissingKey` to return the missing key string unchanged.

## Shipped message bundles

ARDOR ships complete react-admin translation bundles in `packages/admin/src/common/locales/en.ts` (`englishMessages`) and `packages/admin/src/common/locales/vi.ts` (`vietnameseMessages`).

Both bundles structure messages under the top-level `ra` key with twelve namespaces. The full list of keys is in `packages/admin/src/common/locales/en.ts`:

| Namespace | Keys | What it covers |
|---|---|---|
| `action` | 41 | User actions, button labels, and menu items (`add`, `edit`, `delete`, `save`, `export`) |
| `boolean` | 3 | Text representations of boolean states (`true`, `false`, `null`) |
| `page` | 12 | Screen titles, empty states, loading indicators, and error screens (`dashboard`, `list`, `error`) |
| `input` | 4 | File upload, image upload, references, and password field labels |
| `message` | 22 | Confirmation dialogs, validation notices, and system alerts (`are_you_sure`, `delete_content`) |
| `navigation` | 17 | Pagination controls, page ranges, filter status, and skip links (`page_range_info`, `next`, `previous`) |
| `sort` | 3 | Column sorting directions and labels (`sort_by`, `ASC`, `DESC`) |
| `auth` | 8 | Authentication inputs, menu options, and sign-in status (`username`, `password`, `sign_in`, `logout`) |
| `notification` | 13 | Toast notifications, HTTP errors, and data provider status messages (`created`, `updated`, `deleted`) |
| `validation` | 10 | Form input validation rules (`required`, `minLength`, `maxLength`, `email`, `regex`) |
| `saved_queries` | 9 | Saved filter query dialogs, labels, and actions (`label`, `query_name`, `new_dialog_title`) |
| `configurable` | 6 | UI customization inspector titles, element labels, and toggle controls (`inspector`, `customize`) |

When adding custom messages, spread the base bundle and define your translations under a dedicated top-level namespace such as `app`.

> [!WARNING]
> Object spreading is shallow. Writing `{ ...englishMessages, ra: { action: { save: 'Save changes' } } }` replaces the entire `ra` tree. To override individual framework keys, spread the nested subtrees or declare custom messages in a distinct namespace.

## Feature-contributed messages

Features mounted by the application contribute localized messages through the `messages` property of `TFeature` (see [Features](./features)).

In `packages/admin/src/features/messages.ts`, `FeatureMessages` coordinates feature translations:

- Feature messages are merged flat per locale without prefixes. If two features declare identical translation keys, `FeatureMessages.combine()` throws an error naming both features to prevent silent collisions.
- In `DefaultI18nProvider.composeMessages()`, feature messages are passed as base messages, and the application's `i18nSources` are merged over them using `lodash/merge`. The application can therefore override or relabel any feature message.
- Features may provide lazy message loaders: `() => Promise<object>`. When a feature specifies a lazy loader for the active initial locale, `ArdorApplication` in `packages/admin/src/components/application.tsx` invokes `i18nProvider.changeLocale()` to load the bundle before rendering the administration interface.

## Hooks that read or update the locale

ARDOR provides four hooks that interact with the active locale and internationalized messages:

| Hook | Signature | What it does | Where to call it |
|---|---|---|---|
| `useTranslate` | `() => TUseTranslateFn` | Returns a typed `translate(key, options?)` function. Returns the typed function when `useI18nProvider()` returns a provider, otherwise an identity function (`packages/admin/src/hooks/use-translate.ts`). | Inside any component rendered within the react-admin tree (or outside with identity fallback). |
| `useRequestHeaderLocale` | `(opts?: IUseRequestHeaderLocaleOptions) => void` | Synchronizes the active locale from `useLocaleState()` into `DefaultRestDataProvider` request headers using `useInjectable()` on `CoreBindings.DEFAULT_REST_DATA_PROVIDER`. Header key defaults to `HeaderConstants.X_LOCALE` (`'x-locale'`). | Inside a component mounted inside both the application context and the react-admin tree. |
| `useHtmlLang` | `() => void` | Synchronizes document `<html lang>` with the active locale from `useLocaleState()` (`packages/admin/src/hooks/use-html-lang.ts`). | Inside any component rendered within the react-admin tree. |
| `useDocumentTitle` | `(opts: IUseDocumentTitleOptions) => void` | Sets `document.title` to the given screen title segments joined with `appTitle`. Restores previous title on unmount if unchanged (`packages/admin/src/hooks/use-document-title.ts`). | Inside page or layout components. |

The three companion hooks can be mounted together in an administrative layout component:

```tsx
import {
  useDocumentTitle,
  useHtmlLang,
  useRequestHeaderLocale,
  useTranslate,
} from '@venizia/ardor';

export const AdminLayoutSync = () => {
  const translate = useTranslate();

  useHtmlLang();
  useRequestHeaderLocale({ key: 'accept-language' });
  useDocumentTitle({
    title: translate('ra.page.dashboard'),
    appTitle: 'Store Admin',
  });

  return null;
};
```

`useRequestHeaderLocale` must be placed in a component mounted inside both the application context and the react-admin tree because it uses `useInjectable` on `CoreBindings.DEFAULT_REST_DATA_PROVIDER` and `useLocaleState`. It forwards the active locale to the REST data provider network service (see [Network](./network) and [Data provider](./data-provider)).

To enable type checking for custom application translation keys, augment `IUseTranslateKeysOverrides` in `@venizia/ardor` using `Record<TAppKeys, true>` and `TFullPaths` (see [Module augmentation](../best-practices/module-augmentation) and [Add a language](../guides/tutorials/add-a-language)):

```tsx
import {
  type TFullPaths,
  englishMessages,
  useTranslate,
} from '@venizia/ardor';

const appMessages = {
  ...englishMessages,
  app: {
    welcome: 'Welcome',
    items: {
      empty: 'No items found',
    },
  },
};

type TAppKeys = TFullPaths<typeof appMessages>;

declare module '@venizia/ardor' {
  interface IUseTranslateKeysOverrides extends Record<TAppKeys, true> {}
}

export const ItemNotice = () => {
  const translate = useTranslate();

  return <p>{translate('app.items.empty')}</p>;
};
```
