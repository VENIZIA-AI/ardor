# Internationalization

`DefaultI18nProvider` creates the react-admin internationalization provider (`I18nProvider`) backed by `ra-i18n-polyglot`. `BaseArdorApplication` binds it under `CoreBindings.DEFAULT_I18N_PROVIDER` itself, as a singleton. An application that offers more than English binds its options: a `@configuration()` class with a `@provide({ key })` method, which `start()` binds as a lazy singleton (see [The bind order](../guides/core-concepts/configuration)):

```ts
import {
  configuration,
  CoreBindings,
  englishMessages,
  type II18nProviderOptions,
  provide,
  vietnameseMessages,
} from '@venizia/ardor';

@configuration()
export class I18nConfiguration {
  @provide({ key: CoreBindings.I18N_PROVIDER_OPTIONS })
  i18nProviderOptions(): II18nProviderOptions {
    return {
      i18nSources: {
        en: englishMessages,
        vi: vietnameseMessages,
      },
      languages: [
        { locale: 'en', name: 'English' },
        { locale: 'vi', name: 'Tiếng Việt' },
      ],
    };
  }
}
```

- Default class: `DefaultI18nProvider` from `packages/admin/src/providers/i18n.ts`.
- Options key: `CoreBindings.I18N_PROVIDER_OPTIONS` (`@app/application/options/i18n`). Optional: unbound, the application is English only.
- Provider key: `CoreBindings.DEFAULT_I18N_PROVIDER` (`@app/application/i18n/default`).

The container injects `I18N_PROVIDER_OPTIONS` and the optional `FEATURES` into the provider and passes the result to react-admin (see [Application](./application)). To replace the provider, bind your own class under the provider key in `bindContext()`: `.toProvider(MyI18nProvider).setScope(BindingScopes.SINGLETON)`.

## What it does

| Export | Kind | Meaning |
|---|---|---|
| `DefaultI18nProvider` | class | Provider that builds the react-admin `I18nProvider` from `II18nProviderOptions` |
| `II18nProviderOptions` | interface | Options defining `i18nSources` and `languages` |
| `englishMessages` | const | English translation bundle containing react-admin `ra.*` messages |
| `vietnameseMessages` | const | Vietnamese translation bundle containing react-admin `ra.*` messages |
| `useTranslate` | hook | Returns a typed `translate(key, options?)` function |
| `useUntypedTranslate` | hook | Returns `translate(key, options?)` for a key that exists only at run time |
| `useRequestHeaderLocale` | hook | Synchronizes the active locale with REST data provider request headers |
| `useHtmlLang` | hook | Synchronizes document `<html lang>` with the active locale |
| `useDocumentTitle` | hook | Sets the document title and restores the previous title on unmount |
| `TUseTranslateFn` | type | Function signature returned by `useTranslate` |
| `TUseTranslateKeys` | type | Accepted keys: union of default keys and `IUseTranslateKeysOverrides` |
| `TUseTranslateKeysDefault` | type | `TFullPaths<typeof englishMessages>` |
| `IUseTranslateKeysOverrides` | interface | Overridable interface for augmenting application translation keys |
| `IUseRequestHeaderLocaleOptions` | interface | Options for `useRequestHeaderLocale` |
| `IUseDocumentTitleOptions` | interface | Options for `useDocumentTitle` |
| `CoreBindings.DEFAULT_I18N_PROVIDER` | const | Container binding key for the internationalization provider instance |
| `CoreBindings.I18N_PROVIDER_OPTIONS` | const | Container binding key for `II18nProviderOptions` |
| `HTTP.Headers.LOCALE` | const | Default request header name (`'x-locale'`) used by `useRequestHeaderLocale` |

## Options

`II18nProviderOptions` from `packages/admin/src/common/types.ts` defines the configuration options:

| Field | Type | Default | Meaning |
|---|---|---|---|
| `i18nSources` | `Record<string, TI18nSource>` | `{ en: englishMessages }` | Locale codes mapped to message bundles. |
| `languages` | `Array<Locale>` | `[{ locale: 'en', name: 'English' }]` | Available locales with display names, passed to react-admin. |
| `locale` | `{ persist?: { use: boolean } }` | `{ persist: { use: true } }` | Keeps the chosen locale in `localStorage`. |
| `fallback` | `{ locale: string }` | `{ locale: 'en' }` | The locale whose messages are layered under every other locale. |

- **`i18nSources`:** Each bundle is an object or a lazy loader (`() => Promise<object>`). Merged with feature messages per locale.
- **`languages`:** Each entry is `{ locale: string, name: string }`.

The options apply independently. If `languages` defines a locale code that is missing from `i18nSources`, selecting that locale shows the fallback messages (see [Messages by layer](#messages-by-layer)).

## Lazy sources

A source is the messages object, or a function that returns a promise of it, called the first time its locale is used. A bundler turns `() => import('./vi')` into a chunk that stays out of the boot bundle:

```ts no-check
const i18nProviderOptions: II18nProviderOptions = {
  i18nSources: {
    en: englishMessages, // read at once
    vi: () => import('./vi'), // loaded when the user picks Vietnamese
  },
  languages: [
    { locale: 'en', name: 'English' },
    { locale: 'vi', name: 'Tieng Viet' },
  ], // ...
};
```

- **What a loader returns:** the messages, or an ES module whose default export is the messages (`export default { ... }`, as `import('./vi')` gives). Anything else counts as a failed load.
- **First render:** when the starting locale is lazy, `ArdorApplication` shows `suspense` until its messages arrive, as it does for a feature's lazy messages.
- **A failed load** (a file that does not download, a chunk that did not arrive) does not stop the admin. The error is logged through the provider's `this.logger`, the locale shows the English messages (and the features' messages) and nothing is remembered, so the next `changeLocale()` calls the loader again.
- **A failed feature load is handled the same way.** A feature's lazy bundle that rejects is logged and the locale shows the fallback messages; `changeLocale()` still resolves, so `useLocaleState`, `<html lang>` and the `x-locale` header agree with the screen. The bundles that did load are kept, and the next `changeLocale()` calls only the failed loader again.
- **Loaded once:** after a loader delivers, the messages are kept; a second `changeLocale()` to the same locale does not call it again, and two calls made before it delivers share one call of the loader.

## The chosen locale is kept

By default `changeLocale()` stores the locale in `localStorage` under `@app/prefs/locale` (`@app/prefs/<id>/locale` when the application info has an `id`; `LocalStorageKeys.scoped({ id }).locale`), and the provider reads it first the next time it is built. The key is a preference, so a sign-out does not remove it: `DefaultAuthProvider.clearStoredData` sweeps `@app/store/` only.

- **Only a choice is stored.** `changeLocale()` to the locale already shown stores nothing, so the load of the starting locale at boot does not turn the browser's language into a saved choice.
- **A stored locale that is not in `languages` is ignored**, and a locale outside `languages` is not stored.
- **Outside a browser** (no `localStorage`, or a storage that throws) nothing is stored or read and nothing throws.
- **Turn it off** with `locale: { persist: { use: false } }`; the provider then neither reads nor writes the key.

## Initial locale

In `packages/admin/src/providers/i18n.ts`, `DefaultI18nProvider.resolveInitialLocale` computes the startup locale when `value()` is called. It takes the first match of:

1. The stored locale (see [The chosen locale is kept](#the-chosen-locale-is-kept)).
2. The browser's languages (`navigator.language`, then `navigator.languages`), in order. Each is tried as the full tag (`pt-BR`), then as its primary subtag (`pt`), against the locales in `languages`. The comparison ignores case and returns the locale as `languages` spells it.
3. The first locale in `languages`, so an application that does not offer `en` starts in its own language.
4. `en`, when `languages` is empty.

| Browser language | Configured `languages` | Initial locale |
|---|---|---|
| `en-US` | `['en', 'vi']` | `en` |
| `vi-VN` | `['en', 'vi']` | `vi` |
| `fr-FR` | `['en', 'vi']` | `en` |
| `fr-FR` | `['vi']` | `vi` |
| `en-US` | `['vi']` | `vi` |
| `pt-BR` | `['pt-BR', 'en']` | `pt-BR` |
| `zh-TW` | `['zh-CN', 'zh-TW']` | `zh-TW` |

Without a `navigator` there is no browser language, so the first locale in `languages` is used. With nothing stored and no browser language that `languages` offers, the app starts in `languages[0]`: put the language you want as the default first. There is no option for another start language; to choose it another way (a user profile, a server setting), subclass `DefaultI18nProvider`, override `resolveInitialLocale`, and bind the subclass under `CoreBindings.DEFAULT_I18N_PROVIDER` in `bindContext()`. An override replaces all of this, the stored locale included.

Missing translation keys do not throw: `polyglotI18nProvider` sets `allowMissing: true` and `onMissingKey` to return the missing key, with its `%{token}` and plural forms filled as for any text. The first time a key is missing in a locale, the provider logs a warning through `this.logger` (`[translate] Missing message <key> for locale <locale>`), once per key and locale, so a typo or an untranslated key shows in the log. A call that passes a default text (`{ _: 'Hello' }`) is not missing.

## Messages by layer

`composeMessages` builds the messages of a locale from five layers. A later layer wins, and plain objects merge key by key:

1. `englishMessages`, ARDOR's own English texts. They are always there.
2. The features' messages of the fallback locale.
3. The features' messages of the chosen locale.
4. The application's `i18nSources` of the fallback locale.
5. The application's `i18nSources` of the chosen locale.

A catalogue can be partial. A key it lacks reads in the layer below, so `ra.action.save` shows `Save` in a language that does not translate it, and a feature that ships only `en` shows its English texts in every locale. An application no longer needs to spread `englishMessages` into its catalogues; one that does keeps working. The fallback locale is `en` unless `fallback: { locale }` names another. A lazy source of the fallback locale loads with the chosen one, and a failed load adds nothing.

## Shipped message bundles

ARDOR ships react-admin translation bundles in `packages/admin/src/common/locales/en.ts` (`englishMessages`) and `packages/admin/src/common/locales/vi.ts` (`vietnameseMessages`), structured under twelve `ra` namespaces:

| Namespace | Keys | What it covers |
|---|---|---|
| `action` | 41 | User actions, button labels, and menu items (`add`, `edit`, `delete`, `save`, `export`) |
| `boolean` | 3 | Text representations of boolean states (`true`, `false`, `null`) |
| `page` | 12 | Screen titles, empty states, loading indicators, and error screens (`dashboard`, `list`, `error`) |
| `input` | 4 | File upload, image upload, references, and password field labels |
| `message` | 22 | Confirmation dialogs, validation notices, and system alerts (`are_you_sure`, `delete_content`) |
| `navigation` | 17 | Pagination controls, page ranges, filter status, and skip links (`page_range_info`, `next`, `previous`) |
| `sort` | 3 | Column sorting directions and labels (`sort_by`, `ASC`, `DESC`) |
| `auth` | 8 | Authentication inputs, menu options, and sign-in status (`username`, `password`, `sign_in`, `logout`) |
| `notification` | 13 | Toast notifications, HTTP errors, and data provider status messages (`created`, `updated`, `deleted`) |
| `validation` | 10 | Form input validation rules (`required`, `minLength`, `maxLength`, `email`, `regex`) |
| `saved_queries` | 9 | Saved filter query dialogs, labels, and actions (`label`, `query_name`, `new_dialog_title`) |
| `configurable` | 6 | UI customization inspector titles, element labels, and toggle controls (`inspector`, `customize`) |

ARDOR's own keys sit under `ardor`: `ardor.access_denied` holds the `title`, `message` and `home` link text of `AccessDeniedPage`.

When adding custom messages, define them under a dedicated namespace such as `app`. The framework keys come from the layer below, so a catalogue lists only the keys it changes, and `{ ra: { action: { save: 'Save changes' } } }` replaces one key, not the whole `ra` tree.

> [!NOTE]
> The English layer is ARDOR's `englishMessages`. Another language shipped with ARDOR, such as `vietnameseMessages`, is not a layer: add it to `i18nSources` under its locale.

## Feature-contributed messages

Features mounted by the application contribute localized messages through the `messages` property of `TFeature` (see [Features](./features)). In `packages/admin/src/features/messages.ts`, `FeatureMessages` coordinates feature translations:

- Feature messages are merged flat per locale without prefixes. If two features declare identical translation keys, the message merge throws an error naming both features to prevent silent collisions. `DefaultI18nProvider.value()` checks the eager bundles of every locale in `languages` and of the fallback locale, so the error shows when the app starts (and in `assertArdorApplicationBoots`), not when a user picks a language.
- In `DefaultI18nProvider.composeMessages()`, feature messages sit above `englishMessages` and below the application's `i18nSources` (see [Messages by layer](#messages-by-layer)), by a deep merge: a later source wins, plain objects merge recursively, and an array or a string replaces. The application can therefore override or relabel any feature message.
- Features may provide lazy message loaders: `() => Promise<object>`. When a feature specifies a lazy loader for the active initial locale, `ArdorApplication` in `packages/admin/src/components/application.tsx` invokes `i18nProvider.changeLocale()` to load the bundle before rendering the administration interface.

## Hooks that read or update the locale

ARDOR provides five hooks that interact with the active locale and internationalized messages:

### useTranslate

- **Signature:** `() => TUseTranslateFn`
- **What it does:** Returns a typed `translate(key, options?)` function. Reads the i18n provider of the tree; with none mounted, ra-core's default provider answers (`packages/admin/src/hooks/use-translate.ts`).
- **Where to call it:** Inside any component rendered within the react-admin tree (or outside it, where ra-core's default provider answers).

### useUntypedTranslate

- **Signature:** `() => TUseUntypedTranslateFn`
- **What it does:** Returns `translate(key: string, options?)` for a key built at run time (`errors.${code}`). It is ra-core's `useTranslate` with a `string` key, and `useTranslate` is that same function with the key narrowed, so both read the same provider and catalogs (`packages/admin/src/hooks/use-translate.ts`).
- **Where to call it:** Inside any component rendered within the react-admin tree (or outside it, where ra-core's default provider answers).

### useRequestHeaderLocale

- **Signature:** `(opts?: IUseRequestHeaderLocaleOptions) => void`
- **What it does:** Synchronizes the active locale from `useLocaleState()` into `DefaultRestDataProvider` request headers using `useInjectable()` on `CoreBindings.DEFAULT_REST_DATA_PROVIDER`. Header key defaults to `HTTP.Headers.LOCALE` (`'x-locale'`). See [Network](./network) and [Data provider](./data-provider).
- **Where to call it:** Inside a component mounted inside both the application context and the react-admin tree.

### useHtmlLang

- **Signature:** `() => void`
- **What it does:** Synchronizes document `<html lang>` with the active locale from `useLocaleState()` (`packages/admin/src/hooks/use-html-lang.ts`).
- **Where to call it:** Inside any component rendered within the react-admin tree.

### useDocumentTitle

- **Signature:** `(opts: IUseDocumentTitleOptions) => void`
- **What it does:** Sets `document.title` to the given screen title segments joined with `appTitle`. Restores previous title on unmount if unchanged (`packages/admin/src/hooks/use-document-title.ts`).
- **Where to call it:** Inside page or layout components.

The three companion hooks can be mounted together in an administrative layout component:

```tsx
import { Ardor } from '@venizia/ardor';

export const AdminLayoutSync = () => {
  const translate = Ardor.useTranslate();

  Ardor.useHtmlLang();
  Ardor.useRequestHeaderLocale({ key: 'accept-language' });
  Ardor.useDocumentTitle({
    title: translate('ra.page.dashboard'),
    appTitle: 'Store Admin',
  });

  return null;
};
```

To enable type checking for custom application translation keys, augment `IUseTranslateKeysOverrides` in `@venizia/ardor` using `Record<TAppKeys, true>` and `TFullPaths` (see [Module augmentation](../best-practices/module-augmentation) and [Add a language](../guides/tutorials/add-a-language)):

```tsx
import { Ardor, type TFullPaths, englishMessages } from '@venizia/ardor';

const appMessages = {
  ...englishMessages,
  app: {
    welcome: 'Welcome',
    items: {
      empty: 'No items found',
    },
  },
};

type TAppKeys = TFullPaths<typeof appMessages>;

declare module '@venizia/ardor' {
  interface IUseTranslateKeysOverrides extends Record<TAppKeys, true> {}
}

export const ItemNotice = () => {
  const translate = Ardor.useTranslate();

  return <p>{translate('app.items.empty')}</p>;
};
```
