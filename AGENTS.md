How to work in the ARDOR repository. **This file is routing only** - it holds no rules and no
facts, it points to where both live. The one exception is what `make vulcan-sync` and `make okf-gen`
generate (the contents list and the rules and atlas blocks), which is never edited by hand.

This is the **only tracked instruction file**. ARDOR's agent tooling is **VULCAN**
(`@venizia/vulcan`, configured in `.configs/vulcan.config.mts`), which writes the gitignored
per-developer adapters (`CLAUDE.md`, `.claude/settings.json`, `.claude/skills/`):

```bash
make vulcan-sync      # re-run after a pull that touched .configs/ or .agents/
make vulcan-doctor    # checks the project still follows VULCAN
```

## Rules that must not be skipped

Full text, cited by ID: `node_modules/@venizia/vulcan/base/rules.md` (V-*) and `.agents/rules.md`.

- V-W-01: this project: `on-user-word` - Git writes happen only on the user's word, in this conversation.
- Pack `venizia` (`node_modules/@venizia/vulcan/base/packs/venizia.md`): this project follows it - V-B-05, V-B-09, V-C-07, V-C-08, V-C-20.
- V-W-02: Never write to a database. Write the migration file, hand over.
- V-W-03: Never deploy or hot-apply (kubectl apply, docker compose up, restarts).
- V-W-06: Approval has a card. Shared writes follow four action classes.
- V-B-08: Scratch and temporary files go in `.agents/local/tmp`, never /tmp or the scratchpad folder a tool offers. Claude Code sets `TMPDIR` to it; elsewhere `export TMPDIR="$PWD/.agents/local/tmp"` from the project root.
- V-P-07: Facts come from atlas, not memory. Before you use an API of the project's framework or of its own packages, look it up with atlas (`symbol`, `search`, `version`, `changes`).
- V-B-03: Run it, read real output, then claim. Evidence before assertions.
- V-P-05: Partner, not stenographer. Wrong instruction → say so with reasoning + better option; human decides.
- V-P-06: Scope discipline: exactly the issue at hand.
- V-B-04: Test first; never green the suite by weakening it.
- V-C-02: One options object first, at most 5 parameters.
- V-C-09: A comment states a lasting fact the code cannot show (a constraint, an external contract, a non-obvious invariant) or is public-API TSDoc.
- V-C-10: No explicit cast in new code. `as X`, `as any`, `as unknown as X` and `as never` assert nothing; they silence the compiler where the type is wrong.
- V-P-08: Reuse before you write. Ask first: does it need to exist at all?
- V-B-07: Say what you skipped. Report plainly what was not done, not checked or left as a shortcut; never let a check that did not run read as one that did.
- V-B-09: Agent scripting uses bun by default. A script you write to do a task is `bun -e '…'` or `bun file.ts`, with `Bun.file()` for files.

## Atlas

The `atlas` MCP server holds the real code and docs of: ardor (this repository), ignis.
Look facts up there before you answer or write from memory (V-P-07):
`symbol` before you use an export (signature, import path, source line); `search`, then `get`, for how something works or which convention applies; `version` or `changes` for a release or an upgrade.
A new app or package: ask `presets` which preset and which `vulcan add` command, run it, and never hand-write package.json, tsconfig or scripts.
How to build something here (a feature, a controller, a service, a repository): `search` first, then `get`, before you answer; a plan never says "check atlas" for a step you have not done.

## Two homes for everything

Nothing lives in two places. Every piece of project information has exactly one home:

- **`.agents/`** - what agents read: ARDOR's rules, the knowledge bundle and the okf renderers.
- **`docs/wiki/`** - the human-facing VitePress site: guides, references, changelogs.

Source code is the ground truth for both. When prose and code disagree, the code wins and the prose
is a bug (V-P-04). The wiki and the bundle are separate audiences; never conflate them (V-C-13).

There are **no per-package agent files** - a package carries no local `CLAUDE.md`. Read its concept
in the knowledge bundle instead.

## The knowledge bundle (`.agents/knowledge/`)

Canonical, tool-neutral facts for ARDOR, in Open Knowledge Format (markdown + YAML frontmatter, one
concept per file, links are the graph edges). Start at `.agents/knowledge/index.md`.

It is also served over MCP by **`atlas`** (registered per machine by `vulcan sync`): VULCAN's atlas
(`vulcan x atlas mcp`) run against this checkout, answering over the
wiki, the changelogs and this bundle:

| Tool | Use it for |
|---|---|
| `search` | Find a chunk by keyword - pass `corpus: "knowledge"` to search this bundle only |
| `get` | Read one chunk in full, by the id a search hit returned |
| `symbol` | An exported symbol's package, signature and source `file:line` |
| `version` | The `@venizia/*` versions a project declares and has installed, next to the newest release |
| `changes` | The changelog entries between two versions of one package, or between two dates |

The full contract, and what goes stale, is in [Atlas MCP server](.agents/knowledge/reference/atlas-mcp.md).

Maintaining it is rule V-P-04: change a fact in the code, update the concept in the same change.
Generated content (P-03) comes from `make okf-gen`; `make okf-check-strict` validates and is not a commit
gate. The `docs-update` skill (shipped by VULCAN) keeps the bundle in step with the code.

## Shared agent assets (`.agents/`)

```
.agents/
├── rules.md          # ARDOR's rules - W · S · P · B · D · C, cited by ID, on top of the VULCAN base
├── knowledge/        # THE knowledge bundle
├── vulcan.manifest.json # written by vulcan-sync; another project's atlas reads ARDOR through it
└── plans/            # gitignored - saved specs and plans, local to each developer
```

VULCAN ships the shared skills (`docs-writing`, `docs-update`, which applies the D rules of `rules.md`) and hooks (the rules digest,
which also prints the minimap block of `rules.md`, and `guard-writes`); a project adds its own and never redefines a shipped one. A skill is a procedure
you follow; a concept is material you consult. Neither is duplicated in the other. Before adding a
skill, check the task is not already covered by one here, by VULCAN or by Claude Code.

## Per-tool files (CLAUDE.md)

This `AGENTS.md` is the single source. `make vulcan-sync` writes `CLAUDE.md` as one line,
`@AGENTS.md`, never a copy. `.claude/` is gitignored, so what everyone shares is declared in
`.configs/vulcan.config.mts` and merged into your `.claude/settings.json` by the same sync, over your
personal keys: VULCAN's rules digest (with the minimap shape) and `guard-writes`, which asks before
a database write, a deploy or a mutating HTTP call. Nothing else blocks a command.
