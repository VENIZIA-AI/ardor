# ardor

`@venizia/ardor` is the umbrella package. It has almost no code of its own - two entry points made of re-export statements. The root (`src/index.ts`) is three:

```ts
export * from '@venizia/ardor-kernel';
export * from '@venizia/ardor-react';
export * from '@venizia/ardor-admin';
```

Everything an application needs - the container and binding primitives from [kernel](/packages/kernel.md), the typed hooks from [react](/packages/react.md), and the react-admin wiring from [admin](/packages/admin.md) - is reachable through one import: `import { ... } from '@venizia/ardor'`. This is the entry point most applications should use. A consumer that only needs one layer can install that sub-package directly instead of pulling in the whole stack.

The one exception is the socket client. `@venizia/ardor/socket-io` (`src/socket-io.ts`) re-exports `@venizia/ardor-kernel/socket-io` - `SocketIOClientHelper` and `ISocketIOClientOptions`. It is deliberately left out of the root, so `import ... from '@venizia/ardor'` never loads the optional `socket.io-client` peer; only an application that imports the sub-path needs it.

## Install

```bash
bun add @venizia/ardor @venizia/ignis-inversion @venizia/ignis-kernel @venizia/ignis-filter @venizia/ignis-helpers reflect-metadata
bun add ra-core ra-i18n-polyglot react react-dom react-redux @reduxjs/toolkit react-router-dom @tanstack/react-query
```

IGNIS is the backend framework in the VENIZIA family; ARDOR is its frontend sibling and a consumer of it. Inversion of control comes from `@venizia/ignis-inversion`, and the data layer speaks the query vocabulary of `@venizia/ignis-filter`. `@venizia/ignis-kernel` is a required runtime peer of `@venizia/ardor-kernel`: its `./metadata` sub-path supplies the artifact stereotypes and the `MetadataRegistry` that the application base reads, so even the root import needs it. `reflect-metadata` is required for decorator metadata used by the container - see [DI in the browser](/architecture/di-in-the-browser.md). The second line is the react-admin stack the umbrella declares as peers. Add `socket.io-client` only if the application uses the `./socket-io` sub-path.

## The VULCAN preset

`@venizia/ardor` also ships a data-only preset, so `vulcan init --preset ardor` creates a monorepo with a working admin and `vulcan add --preset ardor` adds one to a monorepo that exists (side `frontend`, dev port 5173). The template is `presets/app/`, a sibling of `packages/` (`preset.json` with `workspace:*`, `catalog:` and `peer:` markers, and `files/`, derived from `examples/5-mins-qs`: one `products` resource with list, create and edit pages, REST data provider and i18n, no sign-in). `scripts/vulcan-preset.ts` resolves the markers and writes `packages/ardor/dist/vulcan-preset/app/`, the copy the package publishes; the package's `package.json` names it in the `vulcan` field. The release writes it after the version bump, so a preset always names the release it ships in: the umbrella exact, an IGNIS package exact from the root catalog, a third-party package the catalog range. `peers` carries the range this package peers on for each IGNIS package, plus `@venizia/dev-configs` at `^0.3.4` (the `devz` lint command and the `/linters/oxlint` subpath the generated oxlint config imports are new in 0.3.4), and `add` refuses a monorepo whose catalog pins one outside it. `scripts/preset-smoke.ts` (`make preset-smoke`) packs the four packages, reads the preset from the extracted tarball and creates an app in a temp folder outside the repository: the app has the script names of every app (see [App script standard](/conventions/app-script-standard.md): `server:dev`, `compile`, `typecheck`, `lint`, `lint:fix`, `test`, `clean`; `compile` is `vite build --config .configs/builders/vite.config.mts`, `clean` is `devz clean`, and there is one test) and must pass `typecheck` (`bun check`, which reports what `tsc` reports; the smoke plants a type error and expects the script to fail), `lint` (`devz lint`, the `devz` bin of `@venizia/dev-configs` 0.3.4 and later; the smoke plants a badly formatted file and checks `lint` fails, `lint:fix` repairs and `lint` passes) `test` and `compile`, and `vulcan doctor`; the refusal and the pair with IGNIS backends (`IGNIS_DIR`) are scenarios of the same script. The app is silent on its first run: the config is `.configs/builders/vite.config.mts` (the app is CommonJS, so a `.ts` config makes Vite warn about its native config loader), `build.rolldownOptions.output.codeSplitting` splits React and the vendor libraries so no chunk passes 500 kB, and `preset.json` carries `urls: ["/"]` for VULCAN to print; the smoke starts `bun run server:dev`, compiles the app, checks that `clean` removes `dist`, checks that the app root holds only `.configs/`, `src/`, `package.json`, `tsconfig.json`, `.env.example` and `components.json` (the shadcn CLI looks for it there), and fails on any `(!)` or "warning" line in either output. The Vite root is `src/` (`index.html` is `src/index.html`), the output goes to `../dist`, and there is no `README.md` or `scripts/` in the preset (`vulcan add` writes the app's knowledge page). `.configs/builders/Dockerfile` and `nginx.conf.template` build and serve the app (stages deps, builder and production; nginx-unprivileged on 8080 with an SPA fallback; `/api` goes to `API_UPSTREAM`, default `http://api:3000`, through the image's `/etc/nginx/templates` envsubst); it is built from the monorepo root with `docker build -f {{appPath}}/.configs/builders/Dockerfile .`, copies the whole context (the root `.dockerignore` filters it) because the preset cannot know which workspace packages the app needs, and a project can list the packages by hand for better caching, as BANA's `web-manager-lite` does. It also opens the dev server in headless Chrome (`playwright-core`; the installed Google Chrome, or the binary named by `CHROME_BIN`), answers `/api/products` in the browser and checks that the list, its rows and the create form render with no uncaught error and no console error: a dev server that answers 200 for every file can still serve a blank page. The app is styled with Tailwind CSS v4 and shadcn-style components copied into it, the BANA way: `components.json` (style `base-vega`, aliases on `#src/...`), `cn` in `src/utilities/tw.utility.ts`, components in `src/components/shadcn/` (button, card), the CSS-variable tokens of ARDOR's Tide palette in `src/themes/index.css` (a light set and a dark set under `prefers-color-scheme`, no class and no toggle), lucide as the configured icon library (the page uses no icon, so the package is not a dependency yet), and one page, `src/pages/home.tsx`, mounted as the admin's `dashboard`: the drop logo, the app name and the message of `GET /api/hello`, fetched with `useQuery` over the data provider's `send` (so the `/api` prefix and the request headers apply); it has three states, a placeholder while loading, the message, and a line with the command `bun run server:dev` and a retry button when the backend is unreachable. Tailwind is configured only in that CSS file; the one Vite-specific line is the `tailwindcss()` plugin of `.configs/builders/vite.config.mts` (with `@tailwindcss/vite` in the devDependencies), which Bun's `bun-plugin-tailwind` can replace without touching a component. Of BANA's layers it takes the token layer, the `cn` util and the shadcn layout, and skips the palette, derived-colour and density tiers, the chart, editor and icon sheets, the accessibility settings store and the PWA. The app imports its own modules as `#src/...` through the `imports` field the preset declares (VULCAN writes it into the app's `package.json`); there is no Vite alias and no tsconfig `paths`, and the smoke checks the field, that nothing reads `@/`, that dev serves `#src` modules, and that the bundle holds `AdminConfiguration`. The template is outside every package, so no package lint reaches it (there is no `LINT_IGNORE` any more): the generated app lints itself.

## The library preset

`vulcan add --preset ardor --lib <name> [--dir <folder>] [--scope @x]` adds an ARDOR feature package to a monorepo (VULCAN's library kind, contract v1: `vulcan.lib` in `packages/ardor/package.json` names `dist/vulcan-preset/lib/preset.json`). The template is `presets/lib/` (`preset.json` and `files/`), the app's is `presets/app/`; `scripts/vulcan-preset.ts` writes both to `dist/vulcan-preset/{app,lib}/`, resolves the markers of each (`workspace:*`, `workspace:^`, the release version behind a caret, `catalog:`, `peer:`) in `dependencies`, `devDependencies`, `peers` and `peerDependencies`, and gives the lib the app's `.configs/lints/` and `.configs/formatters/`, so both kinds lint the same way (a lib file of the same path wins: `scripts/clean.sh` and `tsconfig.json` are the lib's own). VULCAN writes the `package.json` (version 0.0.0, private, `exports` `.` at `./src/index.ts`, `imports` `#src/*`, `catalog:` ranges), so `files/` has none. A name appears once in the catalog, so a package listed as a peer and as a dev dependency (`@venizia/ardor`, react, react-dom, react-router-dom, reflect-metadata) takes the same marker in both. Scripts are `typecheck`, `lint`, `lint:fix`, `test` and `clean` (the app standard minus `server:dev` and `compile`: no bundler, no dev server), and `checks` are typecheck, lint and test. The tokens are `{{project}}`, `{{lib}}` and `{{package}}`; there is no `{{app}}`, `{{devPort}}` or `{{apiUrl}}`. The sample is `src/feature.ts` (`export const feature = Features.define({ name: '{{lib}}' })`, a fixed export name so a lib name with a dash stays valid), `src/index.ts`, and `src/feature.test.ts`, which mounts the feature in a probe application and reads it back with `Features.read`. The test sits beside the source, not in a `__tests__` folder, because the package's `files` leave `__tests__` out of the tarball and the test would never reach a generated library (the smoke caught it: `bun test` found no test). It differs from BANA's hand-made `auroras/features/merchant` on purpose: no workspace dependencies on BANA's kits, no copied lint script (`devz lint` runs it), a `clean` script, no `Makefile`, no BANA lint overrides (`FEATURE_IMPORTS`, the local rule overrides), the export named `feature` and not `merchantFeature`, and `catalog:` for every version.

## Why an app augments the umbrella

Two of the typed hooks - `useInjectable` from ardor-react and `useTranslate` from ardor-admin - accept a union of string-literal keys built from an empty override interface plus a default set (see [Module augmentation](/architecture/module-augmentation.md)). `IUseInjectableKeysOverrides` is declared inside `@venizia/ardor-react` and `IUseTranslateKeysOverrides` inside `@venizia/ardor-admin`; the umbrella re-exports both with `export *`.

TypeScript follows an `export *` chain to the module that declares an interface, so a `declare module '@venizia/ardor'` block merges into both and the typed key unions pick up the keys. This is the target to use: an application depends on `@venizia/ardor` alone, and under a linker that does not hoist (Bun's `isolated` linker, pnpm) `declare module '@venizia/ardor-react'` fails with TS2664 because that package is not resolvable from the application.

## What this means day to day

- Regular application code (bindings, components, hooks) can and should import from `@venizia/ardor` - that is the whole point of the umbrella.
- Type augmentation files (usually a single `augmentations.d.ts` or similar) must target the specific sub-package, not the umbrella, or the augmentation is a no-op.
- Because the umbrella is just re-exports, there is no umbrella-specific behavior, binding, or lifecycle to document beyond what is covered in [kernel](/packages/kernel.md), [react](/packages/react.md), and [admin](/packages/admin.md) - see [Application lifecycle](/architecture/application-lifecycle.md) for how those three layers cooperate at runtime.
- ARDOR (this whole family of packages, umbrella included) was previously shipped as `@minimaltech/ra-core-infra`; the split and rebrand did not change this re-export-only structure of the umbrella.

For where `packages/ardor` sits relative to `kernel`, `react`, and `admin` in the repo tree, see [Monorepo layout](/overview/monorepo-layout.md). For build and test commands that apply across all packages including this one, see [Build, run, test](/overview/build-run-test.md).
