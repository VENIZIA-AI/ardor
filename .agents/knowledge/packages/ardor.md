# ardor

`@venizia/ardor` is the umbrella package. It has almost no code of its own - two entry points made of re-export statements, and one Node-only entry (`./vite`, below). The root (`src/index.ts`) is four:

```ts
export * as Ardor from './ardor';
export * from '@venizia/ardor-kernel';
export * from '@venizia/ardor-react';
export * from '@venizia/ardor-admin';
```

Everything an application needs - the container and binding primitives from [kernel](/packages/kernel.md), the typed hooks from [react](/packages/react.md), and the react-admin wiring from [admin](/packages/admin.md) - is reachable through one import: `import { ... } from '@venizia/ardor'`. This is the entry point most applications should use. A consumer that only needs one layer can install that sub-package directly instead of pulling in the whole stack.

The one exception is the repository runtime. `@venizia/ardor/repository` re-exports `@venizia/ardor-kernel/repository`; it is left out of the root because it is larger than the whole kernel budget.

## The `Ardor` namespace

`export * as Ardor from './ardor'` (`src/ardor.ts`) gathers the 30 hooks of ardor-react (22) and ardor-admin (8) under one name, so `Ardor.useRepository()` works. It can only live here: react cannot import admin (C-18), and the two packages keep exporting their own top-level hooks, which `Ardor.useX` equals (`expect(Ardor.useX).toBe(useX)` in `src/__tests__/ardor.test.ts`). The decision, with its reasons:

- **A module namespace, not an object literal.** `Object.freeze({ useA, useB, ... })` made `Ardor` reachable only as a whole: measured with `bun build` and a Vite library build, an app that imports one hook through the literal carried all of them, +9.5 KB brotli (1.5 KB for `useRepository` by name, 11.0 KB through the literal). A module namespace is resolved by the bundler at `Ardor.useX`, so the same app is 1,513 B against 1,510 B by name (Bun) and 1,517 B against 1,517 B (Vite/Rollup), and 9,086 B against 9,054 B for `ArdorApplication` plus one hook. A computed read (`Ardor[name]`) keeps every member, so the wiki tells readers not to write one.
- **The Rules of Hooks see it.** oxlint `react/rules-of-hooks` and eslint-plugin-react-hooks treat `Ardor.useX()` as a hook when `Ardor` is a PascalCase identifier. The test lints a valid and a conditional fixture with the react package's own oxlint config: the first passes, the second is reported as `useRepository` called conditionally, so the rule does recognise the call. A nested `Ardor.react.useX` would not be recognised, and a hook body written inside a class static is rejected, which is why the members are references to the top-level functions.
- **The bare hooks are not deprecated.** `@venizia/ardor-react` and `@venizia/ardor-admin` are installable on their own and use each other (admin calls react's `useInjectable`), and neither can name `Ardor`; a `@deprecated` tag would point a react-only project at a namespace it cannot import and mark the packages' own calls. The bare names stay supported.
- **Budget.** The root entry measures every export (`import: "*"`), so each hook the namespace holds adds to it: its limit is 740 B (719 B measured, with the 30 hooks). That row is the glue of the entry, not what an application pays.

## The `ardor` bin: the namespace codemod

`ardor codemod namespace [paths...] [--hooks] [--write [--allow-dirty] | --check]` (run as `bun run ardor ...`: bunx would look the name up on npm; `src/codemod/`, `bin` `ardor` -> `dist/codemod/bin.js`) moves the names removed after 0.4.6 to what replaces them: the bare functions to class members (`isDefined` to `ValueUtility.isDefined`, `getRuntimeConfig` to `RuntimeConfig.get`, ...; `FunctionRenames`), `NumberIdType`, `StringIdType` and `NullableType` to the plain type they were (`TypeRenames`), the kernel logger stack to IGNIS's (`LoggerRenames`, `src/codemod/logger.ts`: `BaseHelper`, `LogLevels`, `ILogger` and `TLogLevel` change their import to `@venizia/ignis-helpers/core`, `Logger.getInstance({ scope })` and `new Logger({ scope })` become `LoggerFactory.getLogger([scope])` with `enableDebug` dropped and a `note` printed, a `Logger` type becomes `ILogger`; it follows the import source, so a `BaseHelper`, `LoggerFactory` or `ILogger` the file defines or imports from elsewhere is left alone, and when such a file also uses `Logger`, IGNIS's name is imported under an alias, `IgnisLoggerFactory` or `IgnisILogger`), and a list, with file and line, of what was removed with nothing to put in its place (`RemovedNames`: `isEditableTarget`, `TDataCount`, `ISyncFC`, `App.DEFAULT_LOCALE`, two `HeaderConstants`; the `enableDebug` prop of `ArdorApplication`; a `Logger` use with no one-line form). A finding of kind `note` is a change made on purpose and does not count as left for `--check`; `Migration` (`src/codemod/migrate.ts`) chains the passes and takes each finding's line from the original file. `--help` prints the tables. It is the upgrade path for a project, because the old names are gone with no deprecated alias; a name removed later must be added to these tables in the same change. It is Node-only like `./vite`: its own build program (`tsconfig.codemod.build.json`, `types: ["node"]`), outside the main build and outside the purity claim, and it reads source with the `typescript` package, an optional peer (`>=5.0.0`) that every TypeScript project has. It modelled on `devz codemod`: a dry run that writes nothing unless `--write`; `--check` exits 1 while anything would change or is left; inside git it reads the files git knows and `--write` refuses a file with local changes, so git can undo it: the file is printed as `refused <path>` with the way to go on, the summary counts it and the exit code is 1, never a silent skip. `--allow-dirty` (only with `--write`, else exit 2) writes such a file anyway and keeps its other edits, so two codemods can run one after the other in a dirty tree.

- **Syntax only, so conservative.** It reads an import from `@venizia/ardor`, `-kernel`, `-react` or `-admin`, rewrites the import and each use (a shorthand property becomes `name: Owner.member`; a property, key or member with the same name is not a use), and lists with file and line what it will not guess: a name the file also declares, a class name already taken by something else or imported as a type only, a re-export by name. An unused import of a function is left as it is; a type, even from `import type`, is rewritten. Running it twice changes nothing the second time.
- **`--hooks`** moves a hook imported from `@venizia/ardor` to `Ardor.useX`. A hook imported from `@venizia/ardor-react` or `@venizia/ardor-admin` is never touched, because those packages cannot import `Ardor`. It is opt-in because the bare hooks are not deprecated, and `examples/5-mins-qs/src/augmentation.check.ts` keeps both forms on purpose.
- **Run on this repository** (functions only): the preset's `admin.configuration.ts` was the one source file that used a removed name; the wiki and README snippets, which are markdown, were edited by hand and are compiled by `docs/wiki/scripts/check-snippets.mts`.
- **Formatting.** The class names are appended to the import they join, so the import may need `make lint-fix-<package>` or the project's formatter to sort them.

## The `./testing` entry

`@venizia/ardor/testing` (`src/testing.ts`) exports `FakeResizeObserver` (a static class: `install()` swaps `globalThis.ResizeObserver` and returns the restore function, `flush({ element, width, height })` calls every observer of the element; happy-dom's `observe()` does nothing) and `assertArdorApplicationBoots`: it runs `start()`, calls `BindingVerifier.assertResolve` of `@venizia/ignis-inversion` (0.4.6-1) over the namespaces `services`, `repositories`, `datasources`, `components` and `configurations`, then resolves what `ArdorApplication` resolves on mount through `ApplicationProviders.resolve`, `Features.read` / `Features.mount` and `Features.loadMessages` (the three functions `ArdorApplication` shares with it, in `ardor-admin`). `fetch` is replaced by a rejecting function for the run (the data provider builds its network service lazily, so nothing is requested while resolving). It is browser-pure (a purity row) with its own size row (1.1 KB), and it is the one place `@venizia/ardor` imports the core, which is why the umbrella needs `@venizia/ignis-inversion` at `^0.4.6` (every package asks for the same range: `scripts/checks/__tests__/peer-dependencies.test.ts`). The preset's `src/boot.test.ts` calls it on the real `Application`.

## The Node-only `./vite` entry

`@venizia/ardor/vite` (`src/vite/`) holds `buildInfoFile`, a Vite plugin that emits `build-info.json` into the build and serves it on the dev server (the stamp of IGNIS's `BuildInfoResolver`, completed from git under Node, plus the installed `@venizia/*` versions). It runs in Node, in the build of an app, so it has its own program (`tsconfig.vite.build.json`, `types: ["node"]`), is left out of the purity claim (`subpaths: ['.', './repository', './testing']` in `scripts/checks/purity/manifest.ts`) and needs two optional peers: `vite` (8.3.5 or newer) and `@venizia/ignis-boot` (the clean-install claim grants it). The shape of the file, `IBuildInfoFile`, is a type in the kernel, so browser code can import it from `@venizia/ardor`. It is the umbrella's only code under test: `make test-ardor` runs real Vite builds and a real dev server in scratch folders under `.agents/local/tmp`. The preset does not use the plugin; the wiki page [Vite setup](https://ardor.venizia.ai/guides/get-started/vite-setup) documents it with the `output.strictExecutionOrder` flag the preset turns on.

## Install

```bash
bun add @venizia/ardor @venizia/ignis-inversion @venizia/ignis-kernel @venizia/ignis-filter @venizia/ignis-helpers reflect-metadata
bun add ra-core ra-i18n-polyglot react react-dom react-redux @reduxjs/toolkit react-router-dom @tanstack/react-query
```

IGNIS is the backend framework in the VENIZIA family; ARDOR is its frontend sibling and a consumer of it. Inversion of control comes from `@venizia/ignis-inversion`, and the data layer speaks the query vocabulary of `@venizia/ignis-filter`. `@venizia/ignis-kernel` is a required runtime peer of `@venizia/ardor-kernel`: its `./metadata` sub-path supplies the artifact stereotypes and the `MetadataRegistry` that the application base reads, so even the root import needs it. `reflect-metadata` is required for decorator metadata used by the container - see [DI in the browser](/architecture/di-in-the-browser.md). The second line is the react-admin stack the umbrella declares as peers.

## The library preset

`vulcan add --preset ardor --lib <name> [--dir <folder>] [--scope @x]` adds an ARDOR feature package to a monorepo (VULCAN's library kind, contract v1: `vulcan.presets.lib` in `packages/ardor/package.json` names `dist/presets/lib/preset.json`). The template is `presets/lib/` (`preset.json` and `files/`), the app's is `presets/app/`; `scripts/preset/vulcan-preset.ts` writes both to `dist/presets/{app,lib}/`, resolves the markers of each (`workspace:*`, `workspace:^`, the release version behind a caret, `catalog:`, `peer:`) in `dependencies`, `devDependencies`, `peers` and `peerDependencies`, and gives the lib the app's `.configs/lints/` and `.configs/formatters/`, so both kinds lint the same way (a lib file of the same path wins: `scripts/clean.sh` and `tsconfig.json` are the lib's own). VULCAN writes the `package.json` (version 0.0.0, private, `exports` `.` at `./src/index.ts`, `imports` `#src/*`, `catalog:` ranges), so `files/` has none. A name appears once in the catalog, so a package listed as a peer and as a dev dependency (`@venizia/ardor`, react, react-dom, react-router-dom, reflect-metadata) takes the same marker in both. Scripts are `typecheck`, `lint`, `lint:fix`, `test` and `clean` (the app standard minus `server:dev` and `compile`: no bundler, no dev server), and `checks` are typecheck, lint and test. The tokens are `{{project}}`, `{{lib}}` and `{{package}}`; there is no `{{app}}`, `{{devPort}}` or `{{apiUrl}}`. The sample is `src/feature.ts` (`export const feature = Features.define({ name: '{{lib}}' })`, a fixed export name so a lib name with a dash stays valid), `src/index.ts`, and `src/feature.test.ts`, which mounts the feature in a probe application and reads it back with `Features.read`. The test sits beside the source, not in a `__tests__` folder, because the package's `files` leave `__tests__` out of the tarball and the test would never reach a generated library (the smoke caught it: `bun test` found no test). It differs from a feature library made by hand in a downstream project on purpose: no workspace dependencies on that project's kits, no copied lint script (`devz lint` runs it), a `clean` script, no `Makefile`, no lint overrides of that project (`FEATURE_IMPORTS`, the local rule overrides), the export named `feature` and not `merchantFeature`, and `catalog:` for every version.

The lib declares the six `@venizia/ignis-*` packages (boot, connectors, filter, helpers, inversion, kernel) as `catalog:` devDependencies, like the app: a peer range never matches a prerelease, so a lib that listed none would resolve the stable copy next to the app's prerelease (see [Release and publish](../process/release-publish.md)). ## Why an app augments the umbrella

Two of the typed hooks - `useInjectable` from ardor-react and `useTranslate` from ardor-admin - accept a union of string-literal keys built from an empty override interface plus a default set (see [Module augmentation](/architecture/module-augmentation.md)). `IUseInjectableKeysOverrides` is declared inside `@venizia/ardor-react` and `IUseTranslateKeysOverrides` inside `@venizia/ardor-admin`; the umbrella re-exports both with `export *`.

TypeScript follows an `export *` chain to the module that declares an interface, so a `declare module '@venizia/ardor'` block merges into both and the typed key unions pick up the keys. This is the target to use: an application depends on `@venizia/ardor` alone, and under a linker that does not hoist (Bun's `isolated` linker, pnpm) `declare module '@venizia/ardor-react'` fails with TS2664 because that package is not resolvable from the application.

## What this means day to day

- Regular application code (bindings, components, hooks) can and should import from `@venizia/ardor` - that is the whole point of the umbrella.
- Type augmentation files (usually a single `augmentations.d.ts` or similar) target `@venizia/ardor`, the package the application depends on: `declare module '@venizia/ardor'` merges into the interfaces the sub-packages declare (`examples/5-mins-qs/src/augmentation.check.ts` is the typecheck that proves it, keys accepted and rejected). The sub-package is the fragile target: under a linker that does not hoist it fails with TS2664 - see [Module augmentation](/architecture/module-augmentation.md).
- Because the umbrella is just re-exports, there is no umbrella-specific behavior, binding, or lifecycle to document beyond what is covered in [kernel](/packages/kernel.md), [react](/packages/react.md), and [admin](/packages/admin.md) - see [Application lifecycle](/architecture/application-lifecycle.md) for how those three layers cooperate at runtime.
- ARDOR (this whole family of packages, umbrella included) was previously shipped as `@minimaltech/ra-core-infra`; the split and rebrand did not change this re-export-only structure of the umbrella.

For where `packages/ardor` sits relative to `kernel`, `react`, and `admin` in the repo tree, see [Monorepo layout](/overview/monorepo-layout.md). For build and test commands that apply across all packages including this one, see [Build, run, test](/overview/build-run-test.md).
