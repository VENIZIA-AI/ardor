# Internationalization

ARDOR's translation layer is a react-admin `I18nProvider` built with `ra-i18n-polyglot`, wrapped in the same provider pattern used everywhere else in the container: `DefaultI18nProvider` lives in [packages/admin](/packages/admin.md) and extends `BaseProvider<I18nProvider>` from [kernel](/packages/kernel.md).

## DefaultI18nProvider

The provider is constructed by dependency injection - its `II18nProviderOptions` are pulled from the container under `CoreBindings.I18N_PROVIDER_OPTIONS`, the same DI mechanism described in [DI in the browser](/architecture/di-in-the-browser.md). `value()` returns the actual `polyglotI18nProvider` instance that react-admin consumes.

Three options drive it, all optional with defaults:

- `i18nSources` - a map from locale code to a `TI18nSource`: a messages object, or a loader `() => Promise<object>` called the first time the locale is used (`LocaleSources`, `providers/i18n-sources.ts`). Defaults to `{ en: englishMessages }`.
- `languages` - the list of `{ locale, name }` entries react-admin shows as selectable languages. Defaults to `[{ locale: 'en', name: 'English' }]`.
- `fallback` - `{ locale }`, the locale layered under every other. Defaults to `{ locale: 'en' }`.

`composeMessages` layers five sets, later over earlier: `englishMessages`, the features' fallback-locale messages, the features' chosen-locale messages, the application's fallback-locale source, the application's chosen-locale source (`LocaleSources.readNow`). A source is partial by design: a key it lacks reads in the layer below, so a locale without a source, or a feature that ships only `en`, shows English rather than the raw key, and an application need not spread `englishMessages`. The pending check registered in `LazyLocales` covers the fallback locale too, so a lazy fallback loads with the chosen locale.

A lazy source keeps a catalogue out of the boot bundle. The initial read is synchronous (polyglot reads it while it is built), so a lazy initial locale reads English first; `Features.hasPendingMessages` and `Features.loadMessages` also ask `LazyLocales` (a `WeakMap` from the i18n provider to its pending check, filled by `DefaultI18nProvider.value`), so `ArdorApplication` waits for the locale through `changeLocale()` the way it waits for a feature's lazy messages. A loader resolves to the messages or to an ES module whose default export is them (`Symbol.toStringTag === 'Module'`). A loader that rejects or resolves to something else is logged through the provider's `this.logger`, is not remembered (the next `changeLocale()` calls it again) and leaves the locale on the lower layers (English and the features' messages): the admin still renders. A loader that delivered is kept and not called again; two `changeLocale()` calls in flight at once share one call: `LocaleSources` keeps the in-flight promise per locale and `FeatureMessages` keeps each lazy bundle's promise per locale and feature, and both drop it when the load fails.

Missing keys are tolerated by design: `allowMissing: true` plus an `onMissingKey` that returns the key itself, after one `this.logger.warn` per locale and key (a `Set` of `locale:key` built in `value()`). The key is returned through the provider's own `translate(key, { ...options, _: key })`: a default text makes polyglot fill tokens and plural forms, which a bare `(key) => key` handler skipped. A typo or an untranslated key never throws or renders blank - it renders the raw key string and shows once in the log. A call with a default text (`_`) never reaches the handler.

## Failures never split the state

`value()` runs `FeatureMessages.readNow` for every offered locale and the fallback locale before it builds polyglot, so a key two features define (or any `getError` of the merge) throws there. At switch time the polyglot `getMessages` callback never throws and never rejects: a feature load that rejects, or two lazy bundles that collide once loaded, is logged through `this.logger` and adds nothing, and the application's own sources and the lower layers still compose. A failed locale stays pending (`FeatureMessages` records a locale only when all its bundles combined), so the next `changeLocale()` calls the loaders again. `changeLocale()` therefore always resolves, and react-admin's locale state, `<html lang>` and the `x-locale` header cannot disagree with the messages shown. A custom i18n provider is not covered: the shell still throws its rejection from render.

## The chosen locale is kept

`value()` reads `CoreBindings.APPLICATION_INFO` (optional) and, unless `locale.persist.use` is `false`, sets `localeKey` to `LocalStorageKeys.scoped({ id }).locale` (`@app/prefs/locale`, or `@app/prefs/<id>/locale`). The default `resolveInitialLocale` reads it first through `BrowserStorage` with `StorageCodecs.text({ allowed: locales })`, so a stored locale that is not offered reads as nothing. `value()` wraps the polyglot `changeLocale`: after it resolves, a locale that differs from the one shown and is offered is written. The same-locale call is the shell's load of the starting locale at boot (`Features.loadMessages`), which is why it is not a choice. `@app/prefs/` is outside `DefaultAuthProvider.clearStoredData`, which sweeps `@app/store/` only. An override of `resolveInitialLocale` replaces the read.

## Initial locale

`resolveInitialLocale({ locales })` runs when the provider is built, never at import. The default takes the first match of: the stored locale; the browser's languages (`navigator.language` followed by `navigator.languages`), each as the full tag and then as its primary subtag, compared case-insensitively against `locales` and returned in the spelling of `locales` (so `pt-BR` matches an offered `pt-BR`, and `zh-TW` an offered `zh-TW`); `locales[0]`, so an application that does not offer `en` starts in its own language; the literal `'en'` only when `locales` is empty. With no `navigator` there are no browser languages. An override replaces the whole order, the stored read included.

## Message bundles and completeness

`englishMessages` and `vietnameseMessages` are the two bundles shipped with ARDOR, covering the full set of react-admin `ra.*` keys (actions, pages, messages, etc). Because `englishMessages` is treated as the canonical, complete bundle, a completeness test compares `vietnameseMessages` against it to make sure no key is missing from the Vietnamese translation. An application bundle may be partial: the missing keys fall back to English one by one.

## Typed useTranslate

`useTranslate` wraps react-admin's `useI18nProvider` with a typed `translate` function instead of the loosely-typed default. The key type is built from the message bundle itself:

- `TFullPaths<typeof englishMessages>` walks the nested `englishMessages` object and produces a union of its dotted key paths (`ra.action.save`, `ra.page.list`, etc) - this becomes `TUseTranslateKeysDefault`.
- `TUseTranslateKeys` is `TUseTranslateKeysDefault | keyof IUseTranslateKeysOverrides`.
- `IUseTranslateKeysOverrides` is an empty interface by design, meant to be augmented via TypeScript module augmentation - the same technique documented in [Module augmentation](/architecture/module-augmentation.md), applied here to `@venizia/ardor-admin`. Applications add their own translation keys by declaring additional properties on `IUseTranslateKeysOverrides`, which extends what `useTranslate` accepts without touching ARDOR's source.

With no provider mounted, `useI18nProvider()` still returns ra-core's default provider (`I18nContext` has a default value), which returns the `_` text of the options when given, else the key, and fills `%{token}` placeholders; the hook never throws.

`useUntypedTranslate` is ra-core's `useTranslate` typed `() => TranslateFunction`, and `useTranslate` is the same function typed `() => TUseTranslateFn` (a `string` key accepts every `TUseTranslateKeys`, so no cast), which keeps the two from drifting. Use it for a key that exists only at run time (`errors.${code}`); a missing key behaves as in polyglot, with no fallback of its own.

## x-locale header

Because the data layer is a plain REST client (see [Data provider pipeline](/architecture/data-provider-pipeline.md) and [Header protocol](/architecture/header-protocol.md)), the current locale needs to be forwarded to the backend explicitly - react-admin's i18n state is client-side only. ARDOR provides an opt-in way to set an `x-locale` header alongside the other protocol headers, so server-rendered content (emails, generated documents, validation messages) can match the locale the user has selected in the admin UI. This keeps the same header-based contract used for tenant and auth signals, rather than inventing a separate channel for locale.

The mechanism is the `useRequestHeaderLocale` hook, which copies react-admin's current locale onto the default REST data provider's request headers - see the x-locale section of [Header protocol](/architecture/header-protocol.md). Nothing in ARDOR calls this hook - configuring `DefaultI18nProvider` alone sets no header, so an application must call `useRequestHeaderLocale` from a component inside its react-admin tree that stays mounted, such as a custom `layout` passed to `ArdorApplication`, for the backend to receive the locale. Called above `ArdorApplication`, `useInjectable` finds no application context and the hook throws.

A second opt-in hook, `useHtmlLang`, keeps `document.documentElement.lang` equal to the ra-core `useLocaleState()` locale so screen readers pick the right voice. It reads no container binding, only ra-core locale state, and nothing in ARDOR calls it.
