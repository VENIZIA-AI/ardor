# Internationalization

ARDOR's translation layer is a react-admin `I18nProvider` built with `ra-i18n-polyglot`, wrapped in the same provider pattern used everywhere else in the container: `DefaultI18nProvider` lives in [packages/admin](/packages/admin.md) and extends `BaseProvider<I18nProvider>` from [kernel](/packages/kernel.md).

## DefaultI18nProvider

The provider is constructed by dependency injection - its `II18nProviderOptions` are pulled from the container under `CoreBindings.I18N_PROVIDER_OPTIONS`, the same DI mechanism described in [DI in the browser](/architecture/di-in-the-browser.md). `value()` returns the actual `polyglotI18nProvider` instance that react-admin consumes.

Two options drive it, both optional with defaults:

- `i18nSources` - a map from locale code to a `TI18nSource`: a messages object, or a loader `() => Promise<object>` called the first time the locale is used (`LocaleSources`, `providers/i18n-sources.ts`). Defaults to `{ en: englishMessages }`.
- `languages` - the list of `{ locale, name }` entries react-admin shows as selectable languages. Defaults to `[{ locale: 'en', name: 'English' }]`.

The translate function looks up the locale's source (`LocaleSources.readNow`) `?? englishMessages` - so any locale without a matching source silently falls back to English rather than erroring.

A lazy source keeps a catalogue out of the boot bundle. The initial read is synchronous (polyglot reads it while it is built), so a lazy initial locale reads English first; `Features.hasPendingMessages` and `Features.loadMessages` also ask `LazyLocales` (a `WeakMap` from the i18n provider to its pending check, filled by `DefaultI18nProvider.value`), so `ArdorApplication` waits for the locale through `changeLocale()` the way it waits for a feature's lazy messages. A loader resolves to the messages or to an ES module whose default export is them (`Symbol.toStringTag === 'Module'`). A loader that rejects or resolves to something else is logged through the provider's `this.logger`, is not remembered (the next `changeLocale()` calls it again) and leaves the locale on `englishMessages` plus the features' messages: the admin still renders. A loader that delivered is kept and not called again; two `changeLocale()` calls in flight at once may call it twice (no in-flight cache: not worth its bytes against the admin size budget).

Missing keys are tolerated by design: `allowMissing: true` plus an `onMissingKey` that returns the key itself. This means a typo or an untranslated key never throws or renders blank - it renders the raw key string, which is a useful debugging signal.

## Initial locale

The module computes a candidate language once at load time, from `navigator.language`, taking everything before the first hyphen (`en-US` becomes `en`; if `navigator.language` is empty, `en-US` is assumed). At provider-construction time, that candidate is used as the `initialLocale` only if it appears in `listLocales` (derived from `languages`); otherwise the initial locale falls back to the literal `'en'` - not to whatever the first entry of `languages` happens to be.

## Message bundles and completeness

`englishMessages` and `vietnameseMessages` are the two bundles shipped with ARDOR, covering the full set of react-admin `ra.*` keys (actions, pages, messages, etc). Because `englishMessages` is treated as the canonical, complete bundle, a completeness test compares `vietnameseMessages` against it to make sure no key is missing from the Vietnamese translation. Any application-supplied bundle should be checked the same way if it aims to fully replace English rather than fall back to it.

## Typed useTranslate

`useTranslate` wraps react-admin's `useI18nProvider` with a typed `translate` function instead of the loosely-typed default. The key type is built from the message bundle itself:

- `TFullPaths<typeof englishMessages>` walks the nested `englishMessages` object and produces a union of its dotted key paths (`ra.action.save`, `ra.page.list`, etc) - this becomes `TUseTranslateKeysDefault`.
- `TUseTranslateKeys` is `TUseTranslateKeysDefault | keyof IUseTranslateKeysOverrides`.
- `IUseTranslateKeysOverrides` is an empty interface by design, meant to be augmented via TypeScript module augmentation - the same technique documented in [Module augmentation](/architecture/module-augmentation.md), applied here to `@venizia/ardor-admin`. Applications add their own translation keys by declaring additional properties on `IUseTranslateKeysOverrides`, which extends what `useTranslate` accepts without touching ARDOR's source.

With no provider mounted, `useI18nProvider()` still returns ra-core's default provider (`I18nContext` has a default value), which returns the `_` text of the options when given, else the key, and fills `%{token}` placeholders; the hook never throws.

`useUntypedTranslate` is ra-core's `useTranslate` typed `() => TranslateFunction`, and `useTranslate` is the same function typed `() => TUseTranslateFn` (a `string` key accepts every `TUseTranslateKeys`, so no cast), which keeps the two from drifting. Use it for a key that exists only at run time (`errors.${code}`); a missing key behaves as in polyglot, with no fallback of its own.

## x-locale header

Because the data layer is a plain REST client (see [Data provider pipeline](/architecture/data-provider-pipeline.md) and [Header protocol](/architecture/header-protocol.md)), the current locale needs to be forwarded to the backend explicitly - react-admin's i18n state is client-side only. ARDOR provides an opt-in way to set an `x-locale` header alongside the other protocol headers, so server-rendered content (emails, generated documents, validation messages) can match the locale the user has selected in the admin UI. This keeps the same header-based contract used for tenant and auth signals, rather than inventing a separate channel for locale.

The mechanism is the `useRequestHeaderLocale` hook, which copies react-admin's current locale onto the default REST data provider's request headers - see the x-locale section of [Header protocol](/architecture/header-protocol.md). Nothing in ARDOR calls this hook - configuring `DefaultI18nProvider` alone sets no header, so an application must call `useRequestHeaderLocale` from a component inside its react-admin tree that stays mounted, such as a custom `layout` passed to `ArdorApplication`, for the backend to receive the locale. Called above `ArdorApplication`, `useInjectable` finds no application context and the hook throws.

A second opt-in hook, `useHtmlLang`, keeps `document.documentElement.lang` equal to the ra-core `useLocaleState()` locale so screen readers pick the right voice. It reads no container binding, only ra-core locale state, and nothing in ARDOR calls it.
