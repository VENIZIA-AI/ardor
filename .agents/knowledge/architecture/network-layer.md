# Network layer

Every HTTP call ARDOR makes goes down one stack: `DefaultRestDataProvider` asks `DefaultNetworkRequestService` for request props (`getRequestProps`), then calls `doRequest`, which joins the URL through a `NativeFetchNetworkRequest` and hands the request to its fetcher, which calls the platform `fetch`. The transport is the IGNIS one (`@venizia/ignis-helpers/core`); ARDOR keeps no fork of it. `doRequest` has one transport, the IGNIS one; the repositories send through IGNIS's `HttpDataSource` (see [Two clients](#two-clients)). This concept covers the layer from `doRequest` down. What sits on top has its own home: the headers in [Header protocol](/architecture/header-protocol.md), the filter mapping in [Data provider pipeline](/architecture/data-provider-pipeline.md), the one 401 retry in [Auth recovery](/architecture/auth-recovery.md) and a non-2xx or failed request in [Error flow](/architecture/error-flow.md).

## The pieces

- **`NativeFetchNetworkRequest`** (IGNIS, `@venizia/ignis-helpers/core`) holds a base URL and a `NativeFetcher`. `getRequestUrl({ baseUrl, paths })` strips one trailing `/` from the base, prefixes each path segment with `/` when it lacks one and joins the segments with nothing between them, so `['users', '1']` becomes `/users/1`. An empty base throws. The join is strict (`UrlBuilder.join`): a path that is a dot segment (`..`, `%2e%2e`), or carries a backslash, `%5c` or a control character, or leaves the base's origin or path, answers a 400 that starts `[<name>] A request path must stay under the base path`. A relative base (`/api`) resolves against the page's origin, and with no page or worker location it is refused (`Relative baseUrl ... needs a page or worker location`). `getNetworkService()` returns the fetcher, whose `send` resolves the Fetch `Response`.
- **`DefaultNetworkRequestService`** builds one in its constructor, with `queryString: { nullish: 'skip', nested: 'json' }` (below), and keeps it in the protected `networkRequest`. `doRequest` checks `baseUrl` itself before joining, with a `getError` that carries no status (so 400). It keeps no path guard of its own: the refusal above is IGNIS's.

## What doRequest sends

`doRequest` calls `send` with the joined `url`, `method`, `params` (its `query`), `headers` (a call that carries headers sends those alone, see Headers below), `acceptStatus: () => true` and `body` - dropped for `GET`, sent for every other method - and passes its own `Logger` as the second argument. It passes a `signal` and never the fetcher's `timeout` (below).

## Two clients

`doRequest` sends with `NativeFetchNetworkRequest`; the repositories send through IGNIS's `HttpDataSource` (`@venizia/ignis-connectors`, an optional peer allowed only on the `./repository` sub-path by the clean-install claims in `scripts/checks/clean-install/manifest.ts`). Building `doRequest` on the data source would make that peer required for every app, so both clients stay until IGNIS's transport core (path guard, send with retry, `readJsonBody`) is in a required peer. `network-request-parity.test.ts` pins what `doRequest` sends and reads, and `network-request-data-source.test.ts` runs the same cases through an `HttpDataSource` spread with `getDataSourceAuth()`, so the two are checked against each other. They agree on the token header, a JSON body, a filter in the query, a JSON answer and a server error. The differences, each with a test: the data source sends a null query value as the text `null` (`doRequest` leaves it out), rejects a body on a GET with an `ApplicationError` that names the url (`doRequest` drops it), always sends `x-request-count: false` and refuses a header of that name (`doRequest` sends what it is given), sends `application/json` without the charset `doRequest` adds, while a path that leaves the base is refused by both with the same 400 and text, and both resolve a relative base URL only where a location exists. Both clients read a 401 themselves: `doRequest` accepts every status and reads the `Response`, as `HttpDataSource` does for its `onUnauthorized` retry.

## Abort and timeout

- **`signal`.** `doRequest({ signal })` hands it to `send`, for the first send and the retry. ra-core passes one to the four reads only because `value()` returns `supportAbortSignal: true` (`useGetList` and the others read the flag); the writes never get one. Its batched `getMany` uses one caller's signal for the whole batch, so unmounting one `ReferenceField` can abort a sibling's query. A request that waits on the shared refresh stops waiting when its own signal aborts; the refresh keeps running for the other callers. `send()` forwards `ISendParams.signal`. An aborted request rejects with the signal's reason (a `DOMException` `AbortError` for a bare `abort()`), which ra-core does not log and `checkError` resolves for (no status).
- **`timeout`** (`IRestDataProviderOptions.timeout`, `{ use: false }` by default) goes to the service's constructor. Each `doRequest` call, the refresh's own included, makes `AbortSignal.timeout(milliseconds)` and combines it with the caller's signal (`AbortSignal.any`). One catch around the send, the refresh wait, the retry and the body read turns a rejection into a 504 `getError` coded `NETWORK_TIMEOUT_CODE` when the combined signal's reason is the timeout signal's reason; any other rejection, a user abort included, passes through unchanged. A repository request through `HttpDataSource` is not covered (it never reaches `doRequest`), and a provider subclass that overrides `createNetworkService()` must pass `timeout` itself. `AbortSignal.any` needs Chrome 116, Firefox 124, Safari 17.4; the preset declares no browser target.
- **Why not the fetcher's `timeout`.** It calls `abort()` with no reason, so a timeout and a user abort both reject with a plain `AbortError` and cannot be told apart.
- **Validation.** `DefaultNetworkRequestService.assertTimeout` throws unless `milliseconds` is a positive safe integer. Both the service's constructor and `DefaultRestDataProvider`'s constructor call it; the provider's call is what fails `start()`, because the service is built lazily on first use.
- **The shared refresh is never aborted.** The signal never reaches `refresh()`. After the refresh settles, `signal.throwIfAborted()` runs before the retry, so an aborted caller sends no retry while the others do.
- **`signal` is not a filter key.** `getList` and `getManyReference` take it out of the params before the `buildListFilter` hook, and `ListFilterBuilder.build` drops it too, for a subclass that calls the builder with the raw params; every other key is copied into the filter. `CountRestDataProvider` passes it to the count request too.
- **Tests.** happy-dom replaces `AbortSignal`, and Bun's `fetch` refuses its signals (`signal is not of type AbortSignal`); the admin test setup restores the native one.

**Query string.** The transport writes `params` into the url with IGNIS's `toQueryString`, configured by the service as `{ nullish: 'skip', nested: 'json' }`: `undefined` and `null` leave the pair out, a string or number is written as it is, and an object or an array is ONE JSON-encoded parameter (`filter={"where":{}}`, `ids=[1,2]`). That is the shape an IGNIS server reads; the IGNIS defaults would drop the filter object and repeat an array's key. A space is written `%20`. The `?` is used when the url has no query, and `&` when it already has one.

## Body encoding

A body is shaped twice. First `getRequestProps` (`packages/kernel/src/base/services/network-request-base.ts`) builds it from `payload` (`{ data, type }`, an `IRequestPayload`) by `payload.type`, through the protected hook `encodeBody` (which still takes `body` and `bodyType`, so that an override written for those names is not handed the wrapper) and the `RequestBodyEncoder` it delegates to (`packages/kernel/src/utilities/request-body-encoder.ts`) - the `content-type` each type sets is in [Header protocol](/architecture/header-protocol.md):

- **`x-www-form-urlencoded`** builds a `URLSearchParams`. **`form-data`** builds a `FormData`. Both skip a key only when its value is `undefined` or `null`, so `0`, `false` and `''` are sent. A `Date` becomes ISO-8601, an object or array becomes JSON, any other primitive goes through `String()`.
- Only `form-data` carries files: a `Blob` or `File` is appended with its `name` as the filename, and a top-level array or `FileList` becomes repeated entries under one key, each item encoded by the same rules. `x-www-form-urlencoded` carries text only and throws for a `Blob`. The `form-data` branch sets no `content-type`, but it does not remove one either: a `content-type` among the service's stored headers still goes out and replaces the multipart boundary.
- **Every other case** (`json`, `none`, `binary`, or no `payload.type`) passes the body through untouched.

The input names `body` and `bodyType` are gone from `ISendParams`, `IRestRequestOptions`, `IGetRequestPropsParams` and `encode`: `RequestBodyEncoder.assertPayload` throws for either key, and for a `payload` that is not `{ data, type? }`, in the base `send`, `request`, `getRequestProps` and `encode`; an override of one of the first three that does not call the base runs no check. The new key has its own name so that no old request can be read as a new one.

`RequestBodyEncoder.encode` has overloads that type the result: `FormData` for `form-data`, `URLSearchParams` for `x-www-form-urlencoded`, the passed body type for `json`, `none`, `binary` and no type, and `IEncodedBody` (`body: unknown`) for a `payload.type` known only as a `string`. They are types only; `src/__tests__/utilities/request-body-encoder.test.ts` pins them with `@ts-expect-error`.

Then the fetcher passes a string, `Blob`, `ArrayBuffer`, typed array, `FormData`, `URLSearchParams` or `ReadableStream` straight to `fetch` and `JSON.stringify`s a plain object or an array, so a `binary` body is sent as its bytes and a string is not quoted a second time; no body stays no body. A `timeout` is combined with the caller's `signal` through `AbortSignal.any`, so either aborts the request. The request is logged at debug level only, to the logger `doRequest` passes; the body is never logged and the headers pass through `redactSecrets`. With no logger the fetcher logs nothing.

## Traps for a transport author

- **The fetcher's own `timeout` does not time the body read** and aborts with no reason. ARDOR's `timeout` option does neither (above); a caller that sends through `getNetworkService().send` with `timeout` gets the fetcher's behaviour.
- **A call's `headers` replace the defaults; a call with none keeps them.** The service gives the transport no default headers, because IGNIS keeps fetcher defaults and merges them per header: a header removed with `removeHeaders` would still be sent. `toSendHeaders` sends the call's headers alone, or the ones `setHeaders` holds now when the call has none, and `null` for `content-type` when the call names none. The service's headers arrive because `getRequestHeader` merges its own copy into every call. A `doRequest` called without `headers` sends the current service headers and the transport's default `content-type: application/json; charset=utf-8`, except for a raw body (`FormData`, `Blob`, `URLSearchParams`, bytes, a stream) with no `content-type` of its own: it is sent with none, so `fetch` writes the multipart boundary. The `form-data` branch of the body encoder sets no `content-type`, and the fetcher does not add or strip one, so `fetch` writes the multipart boundary - unless a `content-type` header is passed in, which replaces it.
- **ARDOR hands on uppercase methods.** A caller writes `HTTP.Methods.PATCH` (lowercase) or `'PATCH'`; `DefaultNetworkRequestService.toWireMethod` uppercases it in `doRequest`, in `DefaultRestDataProvider.request()` and where the providers call them, so an override of `request` or `doRequest` and the transport get uppercase. An override of `send` gets what its caller wrote. The Fetch standard upper-cases most methods but not `patch`, so a lowercase one would reach the server as written from a browser.

## What comes back

After the retry and the non-2xx throw (an `ApplicationError`, see [Error flow](/architecture/error-flow.md)), `NetworkResponseReader.read` (`packages/kernel/src/utilities/network-response-reader.ts`) decodes a 2xx response:

- A 204 returns `{ data: {} }`. With a `schema` a textual body is parsed as JSON whatever its type says, and a textual body that is no JSON, a 204, and an empty body with no content type that is no attachment throw a `FetchSchemaError` (502, issue `invalid_json`) as the IGNIS fetchers do, without calling the schema. A JSON `null` and a file still reach the schema. Whatever `parse` throws, a bug inside it included, also becomes a `FetchSchemaError` (502), with the thrown `issues` or one `custom` issue. A `DATA_WITH_COUNT` list reads `count` by `NetworkResponseReader.parseCount` (non-negative integer or digit string).
- A `content-disposition` of type `attachment` (as IGNIS's `HttpResponseReader.parseContentDisposition` reads it, any case), or a `content-type` that is missing or not textual per `NetworkResponseReader.TEXTUAL_RE`, returns the blob as `data` (IGNIS's `HttpResponseReader.readFile`), plus `filename` (`filename*=` first, then a quoted, then a bare `filename=`; a `filename*` that cannot be decoded is dropped and the plain `filename` is used; the public `NetworkResponseReader.readFilename({ headers })` returns the same name through the same parser) and `contentDisposition` when present.
- Anything else is read as text by IGNIS's `HttpResponseReader.readBody`: an empty body is `null`; a JSON content type is parsed, and a body that claims JSON and is not is a `502` `ApplicationError` that names the type and the length, never the content; any other textual type (`text/plain`, `text/csv`, XML) is returned as its text. `convertResponse` then reads the totals described in [Header protocol](/architecture/header-protocol.md).

A 2xx response with no `content-type` comes back as a `Blob`.

## Replacing the transport

Three seams, widest first. A provider subclass overrides `request()` - one override moves every method and `send()`; [ipc-data-provider](/examples/ipc-data-provider.md) walks the older, per-method form. A `DefaultRestDataProvider` subclass can assign its own `DefaultNetworkRequestService` subclass to the protected `networkService` and override `doRequest`. Narrowest, a service subclass can assign the protected `networkRequest` an IGNIS `NativeFetchNetworkRequest` (or a `BaseNetworkRequest<'native'>` with its own fetcher). That fetcher must resolve a Fetch `Response`: `doRequest` reads `status`, `headers.get`, `text()` and `blob()` from it.

## The socket client

ARDOR has none. A browser application uses the IGNIS one, `SocketIOClientHelper` from `@venizia/ignis-helpers/socket-io/client`, which has nothing node in its graph and is handed `socket.io-client` by the application: `module` is typed `typeof import('socket.io-client')`, so it takes the whole module (`import * as SocketIOClient`), never `{ io }`. The helper calls `io()` in its constructor and keeps `options` for life, so the wiki pattern is `autoConnect: false`, an `auth` callback that reads the token at each connect, `onConnected: () => helper.authenticate()` (the IGNIS server drops a socket that does not authenticate within `authenticateTimeout`, and nothing re-authenticates after a reconnect on its own), and `DefaultAuthProvider`'s `onSessionStarted`/`onSessionCleared` to connect and disconnect. `emit` with a `callback` uses `setImmediate` (absent in browsers); `subscribe` ignores a second handler for an event unless `ignoreDuplicate: false`; `unsubscribe` takes a `TSocketIOEventHandler` of `unknown`. `socket.io-client` is not installed in this repository, so the snippet gate cannot compile the service fence of [Socket.IO client](/extensions/socket-client) (it is `ts no-check`).
